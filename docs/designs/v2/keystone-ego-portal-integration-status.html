一、结论摘要

当前系统已经支持未绑定设备的 DC Plan。

但实际不是“只在首次上传时绑定”，而是 Keystone 会在 workstation 激活、Plan 刷新、任务列表、领取任务和首次上传等多个节点尝试完成绑定。

ego-portal

主要采用用户登录 → 查询 /auth/me → 找 workstation → 使用 workstation_id 激活 → 拉取 /tasks的旧式兼容路径。

上传仍通过 Data Gateway gRPC 完成。

ego-portal-lite

主要采用用户登录 → 使用 Device-Authorization 激活设备 → 刷新 /operator/plans/refresh → 拉取 /tasks的路径。

这一条路径与 Keystone 当前新增的设备激活和 Plan 刷新逻辑更匹配。

当前最重要的兼容前提： ego-portal 仍要求在进入 workstation 激活之前，先从 /auth/me 找到与本机设备匹配的 workstation。如果此时 workstation 尚不存在，它可能会在 Keystone 自动绑定逻辑执行前就失败。

二、Keystone 当前的真实行为

Keystone 已经把“Plan 必须先绑定设备”改成了“Plan 可以先存在，之后再与具体设备建立归属”。

2.1 DC Plan 可以没有设备

当前 dc_plan.dc_device_id 可以为 NULL：

dc_plan
├── operator = 当前操作员
├── workspace_id = 当前工作空间
└── dc_device_id = NULL

未绑定 Plan 的可见条件大致是：

operator = 当前操作员
AND workspace_id = 当前工作空间
AND (dc_device_id = 当前设备 OR dc_device_id IS NULL)

因此当前操作员可以看到：

  • 已经绑定当前设备的 Plan；
  • 尚未绑定任何设备的 Plan。

最后的 fead623 还去掉了部分 dc_type = 'ego' 限制，因此 Operator Flow 已不再严格只处理 Ego Plan。

2.2 Keystone 有多个绑定触发点

A. workstation 激活

POST /api/v1/auth/workstation/activate 激活过程中，会查找当前 operator/workspace 下尚未绑定且未完成的 Plan，并调用 Hilbert 绑定当前设备。

B. Plan 刷新

POST /api/v1/operator/plans/refresh 会同步 Plan，并尝试绑定未绑定 Plan、创建 pending candidate task。

C. 任务列表

GET /api/v1/tasks 为兼容传统 ego-portal，也会尝试绑定未绑定 Plan 并准备候选任务。

D. 领取任务

Data Gateway 的 assignTaskForDevice 发现 Plan 仍未绑定时，会绑定到当前设备，再创建/预留任务。

E. 首次上传

真实上传前会再次校验 Plan 的设备归属。Plan 已属于其他设备时，当前设备会被拒绝。

绑定语义

绑定主要是从“未绑定”变为“绑定当前设备”，已经绑定到其他设备的 Plan 不应被覆盖。

更准确的现状描述： Plan 可以先不绑定设备，但 Keystone 会在多个客户端交互节点尽早尝试绑定；首次上传是最后一道兜底，而不是唯一的主路径。

2.3 Workstation 当前不是简单按 workspace membership 批量生成

最终代码中，workspace 同步不再因为“workspace 成员 × workspace 下 robot”就无条件批量创建所有 workstation。当前 workstation 主要来自：

  • 已有设备、采集员和 workspace 的关联；
  • 已绑定 DC Plan 的 workstation projection；
  • Plan 设备绑定后调用 EnsureDCPlanWorkstation 创建或复用对应 workstation。

因此，认证激活通常要求先能解析到一个 workstation；Plan 绑定和 workstation projection 负责补齐执行所需的关联。

三、ego-portal 当前如何对接 Keystone

主要代码：ego-portal/backend/app/services/auth_service.py、keystone_client.py、sync_service.py。

3.1 登录与 workstation 激活

POST /auth/login→ GET /auth/me→ 按本机 device_id 找 workstation→ POST /auth/workstation/activate→ 保存 workstation token

当前主流程相当于：

login_keystone()
  1. POST /api/v1/auth/login
  2. GET /api/v1/auth/me
  3. 在 workstations / available_workstations 中按 device_id 找 workstation_id
  4. POST /api/v1/auth/workstation/activate
     body: {"workstation_id": 123}
  5. 保存返回的 workstation-scoped access token

虽然客户端代码提供了 activate_bound_device()，可以发送：

POST /auth/workstation/activate
Device-Authorization: <device-token>
{}

但当前 login_keystone() 的主流程使用的仍是 activate_workstation(workstation_id)。

3.2 任务拉取

ego-portal 主要通过：

GET /api/v1/tasks?status=pending&limit=100&offset=...

拉取任务，并按以下字段过滤和聚合：

  • dc_plan_id
  • workstation_id
  • robot_device_id
  • collector_operator_id

之后把 Keystone 任务同步到本地 SQLite，录制 session 在开始前绑定具体的 Keystone task_id。

3.3 上传路径

上传不走 REST，而走 Data Gateway gRPC：

ExchangeCredential→ CreateLogicalUpload→ 对象存储上传→ CompleteUpload

上传时会携带 task_id、dc_plan_id、workspace_id、capture_id、设备和产品来源等信息。Keystone 会校验这些字段是否与上传会话、任务和当前设备匹配。

3.4 ego-portal 与延迟绑定的关系

正常路径：

已有 workstation → 激活 workstation → Keystone 绑定未绑定 Plan → ego-portal 拉取 /tasks → 录制和上传。

潜在循环依赖：

如果 workstation 尚未存在，ego-portal 会在 /auth/me 阶段找不到匹配的 workstation，并在进入 Keystone 的自动绑定逻辑前失败。

四、ego-portal-lite 当前如何对接 Keystone

主要代码：ego-portal-lite/Platforms/iOS/EgoPortalLiteApp/EgoPortalViewModel.swift。

4.1 登录与设备激活

ego-portal-lite 使用设备凭证激活：

1. POST /api/v1/auth/login
2. POST /api/v1/auth/workstation/activate
   Authorization: Bearer <identity-token>
   Device-Authorization: <persistent-device-token>
   body: {}

Keystone 根据 Device-Authorization 解析：

device token→ robot→ device_id→ workstation

因此 lite 不要求客户端先通过 /auth/me 自己找 workstation_id，和 Keystone 当前设备激活模型更一致。

4.2 Plan 与任务刷新

登录后，lite 会：

  1. 调用 GET /api/v1/auth/me 获取当前 workstation 上下文；
  2. 调用 POST /api/v1/operator/plans/refresh；
  3. 使用 workstation_id 分页调用 GET /api/v1/tasks；
  4. 按 dc_plan_id 将 Plan 和 Task 合并成本地快照。

这条路径会直接命中 Keystone 的新逻辑：Plan refresh 会尝试为未绑定 Plan 绑定当前设备并创建 pending candidate task。

4.3 lite 上传的额外约束

lite 的 Data Gateway 上传 metadata 中明确包含：

  • product = ego_portal_lite
  • dc_plan_id
  • task_id
  • workspace_id
  • checksum_md5
  • checksum_sha256

Keystone 会额外校验 MD5 和 SHA-256 是否与上传会话匹配，且格式必须正确。

当前判断： ego-portal-lite 已经直接使用“设备凭证激活 + operator plans refresh”路径，对 Keystone 新增的延迟绑定机制适配得更完整。

七、当前风险与判断

7.1 主要风险：ego-portal 的 workstation 前置依赖

ego-portal 当前的登录实现要求：

/auth/me 能返回匹配本机 device_id 的 workstation
        ↓
客户端拿到 workstation_id
        ↓
客户端才调用 /auth/workstation/activate
        ↓
Keystone 才能执行激活阶段的自动 Plan 绑定

如果产品预期是“首次设备登录时完全自动创建 workstation 并绑定 Plan”，那么 ego-portal 当前实现还没有完全覆盖该场景。

7.2 当前系统实际上是多点幂等绑定

当前设计通过多个入口提高兼容性：

  • 新客户端走 device-token activation；
  • 旧客户端走 workstation_id activation；
  • 两者都可以通过 Plan refresh 或 task list 触发候选任务准备；
  • Data Gateway 领取任务和首次上传提供兜底校验和绑定。

这增强了兼容性，但也让“Plan 到底在哪一刻完成绑定”的行为不再单一，需要重点观察并发绑定、错误重试以及 workstation 尚未创建时的异常路径。

7.3 最终现状一句话

Keystone 已能让 DC Plan 先脱离设备存在，并在设备激活、Plan 刷新、任务列表或 Data Gateway 操作中绑定到当前设备；ego-portal-lite 已按这套新路径对接，而 ego-portal 仍通过旧的 workstation_id + /tasks 路径接入，并依赖 workstation 在登录前已可被发现。

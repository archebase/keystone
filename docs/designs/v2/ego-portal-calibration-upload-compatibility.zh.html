01

核心范围：复用传输，新增业务落点

Keystone 现有设备上传链路已经覆盖设备初始化、设备凭证交换、STS 临时授权、TOS 分片上传、断点恢复与上传完成通知。本设计不复制这些能力，只在上传意图解析处增加分流。

标定数据不是 Episode：不创建虚假 DC Plan，不创建虚假 Task，也不把 episodes.task_id 改成可空。

本次要完成

  • 保留原任务上传的全部接口和业务行为。
  • 让设备凭证可以上传不绑定数采员、计划和任务的标定 MCAP。
  • 支持一轮标定持续产生多条 Capture，直到任意一条标定成功。
  • 让 Ego Portal 通过无需鉴权的 HTTP 接口查询标定 Session 状态。
  • 让管理员手动触发 Orbit 标定 Job；Python Job 读取 MCAP，并把一对一结果 JSON 直接写入 TOS。

本次不做

  • 不修改 protobuf。
  • 不发布新版公共上传 SDK。
  • 不改变 Episode、Task 或 QA 接口。
  • 不把 Ego 本地账号映射为 Keystone 数采员。
  • 不自动触发标定；每条已上传 Capture 仍由管理员显式启动 Orbit Job。

03

接口 protobuf 兼容行为

04

旧接口的兼容扩展

上传类型判定

client_hints["upload_kind"] 服务端行为
缺失或空字符串 按旧的 task_episode 处理。
task_episode 要求并校验原有 task_id、dc_plan_id、workspace 和 workstation 绑定。
calibration_capture 进入新标定分支，不要求 Task、DC Plan 或 workstation。
其他值 返回 gRPC InvalidArgument。

标定上传 hints

CreateLogicalUpload.client_hints 
{
  "upload_kind": "calibration_capture",
  "calibration_session_id": "7f9af590-75c2-47ad-b6e0-76ebf05c44f7",
  "capture_id": "92cd6f2f-d131-4bf0-9b4a-d96258d09011",
  "attempt_no": "3",
  "checksum_sha256": "64-character-lowercase-hex",
  "source": "ego-portal",
  "local_operator": "local-user"
}

calibration_session_id 和 capture_id 都必须由客户端生成为规范小写 UUIDv4：前者在整轮“持续录制直到首次成功”期间保持不变，后者每条 MCAP 重新生成。服务端必须从 Device JWT 获取 robot_id、device_id 和 workspace_id；客户端不能指定或覆盖设备和空间身份。

服务端生成对象路径

TOS OBJECT KEY 
calibration-captures/{device_id}/{calibration_session_id}/{capture_id}/capture.mcap

CompleteUpload 分流

上传类型 完成动作 明确不做
task_episode 创建 Episode、完成 Task、进入 Episode QA。 无变化。
calibration_capture 保存 MCAP 元数据并将 Capture 标记为 uploaded。 不创建 Episode、不修改 Task、不进入 Episode QA 或云同步。

首次收到新的 calibration_session_id 时，Keystone 惰性创建状态为 running 的 Session；每次创建逻辑上传时，创建或恢复对应 Capture。

05

新增 REST 接口

这些接口承接异步标定状态和结果，不进入公共上传 SDK，也不要求修改 Data Gateway protobuf。

设备状态查询

GET
/api/v1/device/calibration-sessions/{session_id} 无需鉴权；Ego Portal 直接使用不可猜测的 session_id 轮询。
200 RESPONSE 
{
  "session_id": "7f9af590-75c2-47ad-b6e0-76ebf05c44f7",
  "status": "succeeded",
  "successful_capture_id": "92cd6f2f-d131-4bf0-9b4a-d96258d09011",
  "capture_count": 4,
  "uploaded_count": 4,
  "processed_count": 3,
  "updated_at": "2026-08-02T10:20:30Z"
}

processed_count 只统计已经产出并通过 Keystone 校验的结果 JSON；仅完成上传、但因 Session 已成功而直接标记为 superseded 的 Capture 不计入。

  • 接口不要求 Authorization 请求头。
  • Session 不存在：404 Not Found。
  • Session ID 格式非法：400 Bad Request。

Orbit 标定作业与后续 Synapse 查询

GET
/api/v1/calibration-captures admin JWT；按 status、session_id、device_id 分页查询 Capture。
GET
/api/v1/calibration-captures/{capture_id} admin JWT；读取 MCAP 对象位置、SHA-256 和标定上下文。
POST
/api/v1/calibration-captures/{capture_id}/process admin JWT；把已上传 Capture 加入 Orbit 标定队列，重复调用保持幂等。
GET
/api/v1/processing-settings/calibration admin JWT；读取当前标定镜像、最大并发、Revision 和修改人。
PUT
/api/v1/processing-settings/calibration admin JWT；以 expected revision 原子更新镜像 digest 与最大并发。
GET
/api/v1/processing-settings/calibration/history admin JWT；分页读取不可删除的标定处理设置历史。
TOS RESULT OBJECT 
{
  "schema_version": 1,
  "status": "succeeded",
  "algorithm_version": "placeholder-v1",
  "calibration_session_id": "7f9af590-75c2-47ad-b6e0-76ebf05c44f7",
  "capture_id": "92cd6f2f-d131-4bf0-9b4a-d96258d09011",
  "source": {
    "uri": "tos://bucket/calibration-captures/.../capture.mcap",
    "size_bytes": 123456,
    "sha256": "64-character-lowercase-hex"
  },
  "result": {
    "camera_matrix": [],
    "distortion_coefficients": []
  }
}

第一版使用占位 Python 镜像。Keystone 通过 Orbit 的 TOS data bindings 把单条 MCAP 只读挂载到 /bindings/input/capture.mcap，把输出目录挂载到 /bindings/output/。Job 将成功或业务失败结果都写到 calibration-results/{device_id}/{session_id}/{capture_id}/result.json；Keystone 校验 Capture ID、Session ID、源文件大小和 SHA-256 后再更新状态。后续替换真实算法镜像时无需修改上传协议。

Capture 主状态流

uploading
uploaded
calibrating

标定失败的 Capture 进入 failed，但所属 Session 保持 running，Ego 继续录制上传。Session 已成功后才完成的在途 Capture 标记为 superseded。

首条成功原子收敛

提交成功结果时，Keystone 在同一事务中更新 Capture、将 Session 从 running 改为 succeeded，并写入 successful_capture_id。只有第一条成功 Capture 能获胜，后续并发结果不能覆盖。
07

安全、幂等与竞态

公开状态接口

设备状态查询不做身份鉴权。session_id 必须使用规范小写格式、不可枚举的随机 UUIDv4，响应只包含运行状态、计数和成功 Capture ID，不返回对象路径、操作员或其他敏感元数据。响应设置 Cache-Control: no-store，并应用基础限流。

上传幂等

  • 同一设备重复完成相同 capture_id 时，对象路径、文件大小、SHA-256 全部一致则返回成功。
  • 任一字段不一致时返回 gRPC FailedPrecondition，禁止静默覆盖。
  • 同一 Capture 重复调用 POST .../process 不会创建第二个 Orbit 作业。

Session 成功时的在途请求

请求时机 处理策略
成功后新建上传 CreateLogicalUpload 返回 FailedPrecondition，不再签发 STS。
成功前已开始、成功后完成 允许 CompleteUpload 收口对象，Capture 标记为 superseded。
Ego 轮询到 succeeded 不再开始下一段；当前录制正常结束，避免损坏 MCAP，但不再排队上传。
08

发布、兼容与验证

客户端 / 服务端组合 结果
旧 Ego + 旧 Keystone 原任务上传正常。
旧 Ego + 新 Keystone 原任务上传正常，行为不变。
新 Ego + 新 Keystone 任务上传与标定上传均正常。
新 Ego + 旧 Keystone 标定上传不受支持，会因缺少任务绑定而失败。

Orbit 占位作业部署配置

KEYSTONE ENV 
KEYSTONE_CALIBRATION_PROCESSING_ENABLED=true
KEYSTONE_ORBIT_BASE_URL=http://orbit.archebase-system.svc.cluster.local:8080
KEYSTONE_CALIBRATION_POLL_INTERVAL_SECONDS=5

标定镜像和最大并发不再通过环境变量配置。管理员在 Synapse 的“系统设置 → 设备标定”中保存不可变的 @sha256: 镜像引用；Keystone 生成带修改人和时间的数据库 Revision，并在 Capture 提交 Orbit 前冻结 Revision 和镜像。占位镜像由 jobs/calibration-placeholder/Dockerfile 构建；真实算法准备好后，只需发布新镜像并保存新的设置 Revision。

发布顺序不能反转

  1. 先部署数据库迁移和新版 Keystone。
  2. 验证旧 Ego Portal 的任务上传完整回归。
  3. 再部署支持标定模式的 Ego Portal。

回滚 Ego Portal 不影响原任务上传。回滚 Keystone 前必须停止新标定上传，否则旧 Keystone 无法识别 calibration_capture。

验收清单

  • 旧客户端不发送 upload_kind 时仍能创建 Episode 并完成 Task。
  • 标定上传不携带 task、plan、workstation 也能获得受限 STS。
  • 状态查询不携带 Authorization，且响应不暴露对象路径或操作员信息。
  • 同一 Capture 重试 CompleteUpload 不产生重复记录。
  • 失败结果不会结束 Session，首条成功结果会原子结束 Session。
  • Session 成功后的新上传被拒绝，在途上传被安全收口。
  • protobuf 与公共上传 SDK 无变更。
Keystone 保留旧战线，新增标定分流；传输主干不重写，业务语义不混用。

01

决策锁定

  1. 原始 Episode 与 episodes.mcap_path 永不被派生处理覆盖。
  2. 本期只实现硬编码的 stereo_split，不建设动态 Processor、脚本目录或多版本平台。
  3. 当前双目拆分镜像由管理员在 Synapse Data Ops 设置中集中配置，只接受带显式 registry 的不可变 digest；Keystone 不限制仓库，单条和批量作业请求都不能覆盖镜像。
  4. UNIQUE (episode_id, kind) 保证每个 Episode 只有一条当前双目拆分记录；成功后永久跳过。
  5. 一个 generation 对应一个 Orbit Job；失败重试递增 generation，并使用新的独占输出前缀。
  6. 一个持久化 Derivative Reconciler 统一执行冻结请求、提交、轮询、验证、自动 QA 和 Orbit DELETE。
  7. 影响执行的完整 Orbit 请求必须先提交数据库；后续恢复只读取该快照。
  8. 批量处理使用 bulk_run_items 显式保存成员、准入结果和终态，不从当前 Derivative 反推历史。
  9. 同步准入在 sync_logs.source_snapshot 保存实际上传对象；Sync Worker 不再根据 Episode metadata 猜来源。
  10. 一个 Episode 只向 Hilbert 发布 original 或 stereo_split 中的一种，来源认领不可切换。
  11. 派生成功后自动 QA；只有派生 QA approved 后，管理员才能手动同步派生结果。
  12. 第一阶段强制 KEYSTONE_SYNC_AUTO_SCAN_ENABLED=false，原始与派生同步都由管理员动作触发。
  13. 第一阶段 Keystone 保持单副本；数据库仍使用原子状态 claim，扩容时再引入 leader lease。
  14. TOS 原始对象 key 必须不可覆盖；当前 Orbit 不支持按 version ID 固定 binding。
  15. Orbit DELETE 204 表示后台删除请求已接受，404 表示 Job 已不存在；PV/PVC 与可能短暂残留的 Job 继续交给 Kubernetes 和集群 GC 收敛。
02

目标与非目标

目标

  • 在数据明细页与数据操作页提供“双目拆分”的单条和批量入口。
  • 把 split_mcap_stereo_imu.py 封装为唯一当前镜像。
  • 允许管理员在 Data Ops 页面更新唯一当前镜像 digest，并保留不可删除的变更审计。
  • 让 Orbit 保持算法无关，只理解 Job 与 data binding。
  • 跨 Keystone、Orbit 重启恢复排队、执行、验证、Orbit 删除、质检和同步。
  • 保证一个 Episode 只向 Hilbert 发布原始或双目拆分中的一种正式 MCAP。
  • 用 generation 独占前缀隔离失败，成功结果永久跳过。
  • 限制 CPU、内存、临时盘、网络和 TOS 并发。
  • 用显式批次成员和同步快照降低大批量恢复复杂度。

非目标

  • 不替换原始 MCAP，不创建第二个 Episode。
  • 不向 Synapse 暴露通用 Orbit Job 提交能力。
  • 不建设通用镜像市场、凭据管理、多版本选择或按作业指定镜像的能力。
  • 不自动创建任何云同步；第一阶段关闭原始自动 scanner。
  • 不允许原始 MCAP 与双目拆分 MCAP 各自注册 rawDataId，也不提供发布来源切换或重新发布。
  • 处理器镜像不调用 TOS SDK，不接收 AK/SK、STS 或签名 URL。
  • 不直接在 CSI 挂载上运行 rosbags.AnyReader 或 Writer。
  • 处理失败或取消不自动创建新 generation；由管理员明确重试。
  • 不允许用户提交任意镜像、命令或脚本。
  • Keystone不直接访问 Kubernetes，也不逐条验证或删除 PV/PVC。
  • 不实现动态处理器目录、通用 Processor 接口、多版本、generation 历史、通用产物目录、DAG 或常驻 warm worker。
  • 不支持 Keystone 多副本同时运行 Derivative Reconciler。

Keystone 的功能接口

StartStereoSplit(ctx, episodeID, actor) (Derivative, error)
RetryStereoSplit(ctx, derivativeID, actor) (Derivative, error)
CancelStereoSplit(ctx, derivativeID, actor) (Derivative, error)
RunStereoSplitQA(ctx, derivativeID, actor) (Derivative, error)
StartStereoSplitSync(ctx, derivativeID, actor) (SyncLog, error)

本期不定义通用 Processor interface。HTTP handler 只调用这组固定功能接口；同一个 Reconciler 负责所有后台阶段，PV/PVC 最终回收属于集群 GC。

处理时序

  1. 管理员点击“双目拆分”；Keystone锁定 Episode 与 Episode + stereo_split Derivative。若 cloud_publish_source=original，或已有任何原始同步认领证据，则拒绝处理。
  2. 已 succeeded 则返回 already_derived；活跃则返回当前记录；失败或取消且上一 Job 的 Orbit DELETE 阶段已 completed 才递增 generation。
  3. Reconciler 原子领取 queued Derivative，读取当前双目拆分部署配置，并从 Episode metadata 的 backend、bucket、object key 解析规范化 source_uri。
  4. 同一数据库事务生成 orbit_submission_id 与 generation 独占 output_prefix，保存镜像、源对象身份和完整 orbit_request，再把状态改为 submitting；事务提交前禁止调用 Orbit。
  5. Reconciler 从已提交的快照向 Orbit 发起请求；Orbit 创建 PV/PVC 与 Job，Job 将绑定输入复制到 /scratch。
  6. Job 在本地拆分左右图像并解码 IMU，本地校验后复制数据对象。
  7. processing_manifest.json 最后复制到输出 binding；Job 成功退出。
  8. Derivative 进入 verifying；Keystone验证 manifest、MCAP、metadata 和 TOS 对象。
  9. 同一事务写入输出路径、统计、processing=succeeded 与 qa=pending。
  10. Reconciler 保存当前 generation 日志、自动执行双目拆分 QA，并调用现有 Orbit DELETE；PV/PVC 最终回收不阻塞 QA。

手动同步时序

  1. 管理员对双目拆分结果点击“同步到云”；要求 processing=succeeded 且 qa=approved。
  2. 同一事务按 Episode → Derivative → latest sync log 的固定顺序加锁；为 NULL 时原子认领 stereo_split，并创建带完整 source_snapshot 的 pending sync log。
  3. 现有 Sync Worker 只按 sync log 快照读取派生对象，注册或复用 episodes.hilbert_raw_data_id 并上传。
  4. 成功事务更新 Episode 的 canonical cloud_synced、cloud_synced_at、cloud_mcap_path；失败只重试相同派生路径和 rawDataId。

原始手动与管理员批量同步走同一认领事务：只有来源为 NULL / original，且不存在活跃或 succeeded 的双目拆分时，才能创建原始 source snapshot。第一阶段自动 scanner 强制关闭；处理准入与同步准入都先锁 Episode 行，所以并发时只有一方成功。

双目拆分 Job 契约

固定双目拆分契约

buildStereoSplitOrbitRequest(snapshot StereoSplitSnapshot) OrbitJobRequest
verifyStereoSplitOutput(snapshot StereoSplitSnapshot, manifest Manifest) error
runStereoSplitQA(output StereoSplitOutput) QAResult

这三项是 Keystone 内部固定函数，不是可注册插件。出现第二种真实处理功能后，再根据共同点抽取接口。

双目拆分镜像

archebase-cr-cn-beijing.cr.volces.com/prod/orbit-jobs/
  stereo-split@sha256:<configured-digest>

镜像包含 run_processing.py、split_mcap_stereo_imu.py 与固定版本的 rosbags、NumPy、OpenCV headless。它不包含 TOS SDK 或环境专属 bucket。run_processing.py 直接导入 splitter module，并序列化返回的 SplitStats，不得解析人类可读 stdout。

公开命令

python3 /app/run_processing.py \
  --input /bindings/input/<source-object-basename> \
  --output-binding /bindings/output \
  --scratch /scratch \
  --expected-source-size <bytes> \
  --expected-source-checksum <sha256-if-known> \
  --source-uri <frozen-tos-uri> \
  --processor-image <frozen-image-digest> \
  --kind stereo_split \
  --generation <generation>
Orbit 文件 binding 不支持改名：本地输入文件名必须与 TOS object basename 完全一致。目录 binding 的 URI 和本地 path 都必须以 / 结尾。

工作区

/bindings/
  input/<source-object-basename>  # 只读 CSI binding
  output/                         # 可读写 CSI binding
/scratch/
  input/source.mcap
  output_bag/
    output_bag.mcap
    metadata.yaml
  processing_manifest.json

发布纪律

  1. 检查临时盘，复制绑定输入到本地临时名，完整后只在本地 rename。
  2. 校验源大小与可用 checksum；在本地路径运行 splitter。
  3. 校验 output_bag.mcap、metadata.yaml，计算 SHA-256 与大小。
  4. 顺序复制 MCAP 与 metadata 到输出 binding 的最终文件名，并关闭文件等待 CSI flush。
  5. 最后复制 manifest；任何步骤失败都以非零码退出。

对象存储挂载上不执行 rename。generation 前缀始终唯一，因此残缺对象不会覆盖上一代；没有有效 manifest 且未经 Keystone验证的前缀不可见。

输出结构

derived/episodes/123/stereo-split/g2-a6f391/
  output_bag.mcap
  metadata.yaml
  processing_manifest.json

g2-a6f391 中的随机后缀由 Keystone 生成，必须随完整 Orbit 请求在第一次外部调用前持久化；同一 generation 的传输重试不得重新生成。双目拆分当前固定输出一个处理后的 MCAP、一份 metadata 与最后发布的 manifest。以后其他 kind 的输出差异先放在 processing_result JSON，不提前建设通用产物模型。

首次 Reconcile 冻结边界

  1. queued 行尚未绑定某次部署配置；排队期间配置变化时，以 Reconciler 首次领取时看到的当前双目拆分配置为准。
  2. Reconciler 校验 Episode 的 storage backend 为 TOS，并用 metadata 中的 bucket 与 object key 生成唯一规范形式 tos://bucket/key；不得只保存展示路径。
  3. Reconciler 获取源对象大小、ETag 与可用强校验值。原始对象 key 必须不可覆盖；快照冻结后发现身份变化，该 generation 必须失败，不能悄悄改用新对象。
  4. 同一事务写入 processor_image、source_uri、源身份、output_prefix、orbit_submission_id 和完整 orbit_request，并执行 queued → submitting。
  5. orbit_request 是恢复时的唯一请求来源，完整包含 image、command、args、data bindings、resources、deadline、backoff 与 TTL；事务成功提交后才允许第一次调用 Orbit。
关键崩溃边界是“先提交数据库，再调用 Orbit”。若进程在两者之间崩溃，Reconciler 直接发送已存请求；绝不能用新的镜像、资源或随机前缀重建 stale submitting。

输入 binding 的真实范围

TOS CSI 只能挂目录。即使请求声明单个文件，Orbit 也会把对象的父目录挂到 /bindings/input。身份策略与对象布局必须考虑同目录兄弟对象的可见性。

输出 mode 的真实语义

Orbit 当前的 mode: write 实际产生 read-write 挂载。输出前缀必须由服务端生成且 generation 独占，只允许固定的双目拆分镜像接收。

Keystone 验证清单

  • schema、kind、generation、源 URI、镜像 digest 与已冻结 orbit_request 完全一致；源 URI 与镜像 digest 由受信 argv 显式传给 Processor。
  • 输出名固定为 output_bag.mcap 与 metadata.yaml，无目录穿越。
  • 源 URI、大小和可用的 ETag / checksum 符合冻结身份；原始对象未被替换。
  • TOS 输出对象存在、大小与 manifest 一致，并严格位于快照中的 output_prefix。
  • 输出 MCAP 大小为正、头尾 magic 有效；深层 topic / 数量检查归自动 QA。
  • Keystone不为复算 SHA-256 下载完整输出；checksum 由可信镜像产生并结合对象大小、range magic 与后续 QA 使用。

源对象 Stat、manifest 读取、输出对象 Stat 或 range read 的暂时失败会保留 verifying 并递增 verification_attempt_count，最多观察 5 次；超过上限进入 processing failed。manifest schema、冻结快照不匹配、源 size / ETag 漂移和 MCAP magic 错误属于确定性失败，不重试。

Orbit SUCCEEDED 只表示容器成功退出。只有验证通过并在同一事务写入输出字段、processing_status=succeeded 与 qa_status=pending，业务才成功。

提交幂等

orbit_submission_id 对 episode_id + kind + generation 确定。它与随机 output_prefix、源身份及完整 orbit_request 在同一事务中持久化，事务提交后才允许网络调用。当前 Orbit 的 POST 不是严格幂等：它先创建 PV/PVC，再创建 Job，因此 Reconciler 必须按下表收敛，不能把任意 409 当作 Job 已存在。

观察结果Reconciler 动作
GET 返回 Job校验 submission ID、image 与 bindings 后接管，补写 orbit_job_id
GET 404，POST 202保存 Job ID，进入 pending
GET 404，POST 超时保持 submitting；退避后先 GET，不生成新请求
POST 409，随后 GET 返回 Job接管已有 Job
POST 409，随后 GET 仍为 404判定孤儿 binding 冲突；保持 submitting、告警并等待集群 GC 后重试同一快照

已接受 Job 在 pending / running 阶段单次 GET 404 不立即失败：首次观察写 orbit_job_missing_since，连续缺失达到 max(3 × poll interval, 15s) 后才写 processing failed 并释放全局并发容量；期间任何成功 GET 都清空该时间戳。

成功锁与失败重试

  • processing_status=succeeded 是 Episode + kind 永久成功锁。
  • 失败或取消且 orbit_delete_status 为 not_required / completed、cloud_publish_source != original 时，管理员重试会创建新的 generation。
  • 递增 generation 前，重试事务必须先冻结引用旧 generation 的批次 item 结果；存在 admitted 但尚无 result_snapshot 的旧 item 时不得覆盖当前 Derivative。
  • 新 generation 回到 queued，清空 cancel_requested_at、旧请求快照、Orbit Job、处理输出与错误；QA、delete 的状态、attempt、retry time、error、result 与时间戳全部重置，下一次 Reconcile 才冻结当前配置。
  • 上一 generation 的残缺前缀进入延迟对象清理，不保留独立运行记录。
  • 原始同步一旦认领 original，无论 pending、in_progress、failed 或 completed，处理与重试都永久返回 cloud_source_locked。

取消

  • queued 原子改为 canceled，并把 Orbit delete 记为 not_required，不调用 Orbit。
  • submitting / pending / running 先写 cancel_requested_at；它是期望状态，不因一次 Stop 404 被清除。
  • Reconciler 每次 POST 前重查取消标记；POST 已在途时，提交方返回后也必须重查并立即 Stop。
  • submitting 的 Stop 404 只表示“此刻未找到”；若已经尝试 POST，首次 404 写 orbit_submit_absent_at，至少等待 10 秒并再次 GET 仍为 404 后才能写 canceled；期间发现 Job 则按正常 Stop 收敛。尚未尝试 POST 时可直接确认不存在。
  • verifying 及之后拒绝取消。
  • 无有效 manifest 的输出前缀始终不可见，交给延迟对象清理。

Orbit DELETE 与 PV/PVC 最终回收

  1. 捕获 Orbit 终态与有上限的日志尾部。
  2. 成功时完成 manifest 验证；失败或取消时持久化终态原因。
  3. 将 orbit_delete_status 置为 pending。
  4. 同一个 Reconciler 调用现有 DELETE /api/jobs/{job_id}，其他错误持久化并按有上限退避持续重试。
  5. HTTP 204 或 404 都记录 completed 与 orbit_delete_accepted_at：204 表示后台删除请求已接受，404 表示 Job 已不存在；两者都不表示绑定资源已消失。
  6. 集群 GC 按 Orbit labels 扫描孤儿绑定资源，在确认对应 Job / Pod 不存在且超过安全窗口后，依次删除 PVC 与 PV。

Orbit delete 状态只使用 not_required / pending / completed。这里的 completed 只表示 Orbit API 清理阶段已经收敛，不是 Kubernetes 资源消失证明。错误通过 attempt、next_retry_at 与 error 字段表达，不增加无恢复入口的 failed 状态。只有旧 Job 已进入 Orbit 终态，且 delete 为 not_required / completed 才允许 generation 重试；新 generation 使用独立 Job ID、PV/PVC 名称和 TOS 输出前缀，因此不必等待后台删除和物理回收。

GC 只处理带 app.kubernetes.io/managed-by=orbit 与 archebase.io/job-id 的资源；必须验证 Job / Pod 已不存在、资源年龄超过安全窗口，并校验 PV 的 claimRef.namespace 等于 Orbit Job namespace。先删除 PVC，确认消失后再删除 PV。Job TTL 必须长于日志保存与正常 DELETE SLA。

HTTP 204 甚至不保证响应时 Job 已消失；HTTP 204 / 404 也都不保证 PV/PVC 已消失。删除 PV/PVC 只回收绑定资源，绝不能被解释为删除 TOS 前缀中的派生对象。

入队与失败重试事务

单条与批量入口调用同一 seam，并始终按 Episode → Derivative → BulkRunItem / latest sync log 的顺序执行 FOR UPDATE：

  1. 无记录时要求 Episode 尚未认领 original 且无原始同步证据，校验当前可解析到 TOS 源对象，创建 generation 1 queued 行；快照字段保持 NULL。
  2. processing_status=succeeded 时返回或跳过 already_derived，不改任何字段。
  3. 处理活跃、verifying 或上一 Job 的 Orbit DELETE 阶段尚未 completed 时拒绝，避免同一 kind 并行执行。
  4. failed / canceled、delete 为 not_required / completed 且云来源未被 original 认领时，generation 加一，清空执行和输出字段，重置 processing=queued、QA=not_started、delete=not_required。
  5. Episode 删除、越权、源 MCAP metadata 缺失或不能规范化为 TOS URI 时不排队；Reconciler 首次领取时再次解析并冻结真实执行输入。

Reconciler 快照事务不变量

  • queued 允许所有执行快照字段为 NULL；只有 Reconciler 可执行 queued → submitting。
  • 该状态转换必须与所有快照字段一次提交；submitting 行必须拥有完整且可反序列化的 orbit_request。
  • orbit_job_id 只能在 Orbit 响应或查询返回后补写，不属于调用前可知快照；其余影响请求的值都必须先持久化。
  • 发现 submitting 缺少快照属于数据不变量破坏：告警并置为 failed，禁止从当前环境补造请求。

单版本边界

  • 镜像 digest 只回答“这一 generation 实际运行了什么”，不形成可选择的版本。
  • 镜像配置更新后，成功行不变；尚处于 queued 的 generation 在首次调度时读取最新非空数据库 revision，已冻结的 submitting / pending / running generation 继续使用旧快照。没有非空 revision 时处理入口拒绝创建新 generation。
  • generation 不是脚本版本，只是失败重试计数和输出隔离键。

持久化 Worker 与规模化

Derivative Reconciler

  1. 单副本内按全局并发上限扫描到期 Derivative，并用条件 UPDATE 原子 claim。
  2. queued 阶段冻结请求并提交 Orbit；submitting 阶段按 GET / POST 矩阵收敛。
  3. pending / running 阶段轮询 Job；succeeded 后验证 manifest 与 TOS 输出。
  4. processing succeeded 且 QA pending 时运行固定双目 QA；stale QA running 可安全重跑。
  5. 所有 Orbit 终态保存日志，并在同一循环持续重试 DELETE；204 / 404 结束 API 删除状态。generation 达到批次终态时，同一事务冻结引用它的 item result_snapshot。

Bulk Materializer

  • 按页把匹配 Episode 物化为 bulk_run_items，唯一键保证崩溃重扫幂等。
  • 逐条调用与单条入口相同的准入事务，并把 admitted / skipped 原因写回 item。
  • 扫描结束写 materialized_at；finalizer 只聚合 item，不读取 Derivative 当前归属。

容量策略

  • 一个 queued Derivative generation 对应一个 Orbit Job；数据库排队不会提前创建 Pod。
  • 双目拆分固定声明 CPU、内存与 ephemeral-storage request / limit。
  • backoff_limit=0；处理重试必须是业务动作。
  • Job TTL 长于日志保存与 Orbit DELETE SLA；正常情况由 Keystone主动调用 DELETE，残留绑定资源由集群 GC 回收。
  • 批量入口只增加 item 与 queued Derivative，不绕过同一个 Reconciler。
  • 交互式单条请求优先级高于批量请求；二者共享一个全局并发上限。

容量测试必须覆盖 CSI→scratch、scratch→CSI 吞吐、CSI flush 与可见延迟、JPEG 编解码 CPU、峰值内存、输入输出比例、临时盘压力和队列等待时间。

默认全局并发为 1。完成单任务链路验证后，再根据节点 CPU / 内存 / scratch 容量、TOS 吞吐、CSI 挂载能力、Orbit Controller 与自动 QA 能力逐步提高。当前不采用少量常驻 Pod 循环处理：独立 Job 能保留逐条资源隔离、日志、取消和重试边界。只有实测单条处理时间与 Pod + PVC 启动时间同量级时，才另行评估小批 micro-batching。

批量派生：复用 bulk_runs

在现有批量基础设施上增加 stereo_split action，复用筛选、运行记录、SSE 与取消。请求不接收镜像或命令。Materializer 按页写 bulk_run_items 并调用单条准入事务；真正容量仍由唯一 Reconciler 控制。批次历史可以精确回答成员、跳过原因和当次结果。

all_matching 的成员物化语义

  • 创建批次时保存筛选条件、snapshot_max_episode_id 和 preview_counts；页面必须标注“预估”。
  • Materializer 只扫描不超过 ID 上界的数据；每个匹配 ID 先以 INSERT ... ON DUPLICATE KEY 固定 item，再执行准入。
  • item、准入结果、Derivative 变更和 materialize cursor 在同一事务提交；准入成功同时保存 derivative_id + derivative_generation，崩溃重扫同一 ID 直接复用 item 结果。
  • 显式选择模式立即创建请求 ID 对应的 items，但仍在准入时重查权限和业务资格。
snapshot_max_episode_id 仍只是新增数据截止线；preview 可能与最终成员不同，但一旦 item 被物化，该批次的成员和结果不再漂移。

进度、完成与取消

  • 进度至少返回 materializing / admitted / skipped / queued / pending / running / verifying / succeeded / failed / canceled，以及成功项的 QA pending、running、approved、failed和 Orbit delete pending、completed。
  • 活跃计数只在 Derivative generation 与 item 保存值一致时读取当前 Derivative；generation 达到批次终态时写入 item result_snapshot，后续其他批次重试不会改写旧 item。
  • finalizer 必须先锁 bulk run 并确认 materialized_at IS NOT NULL、没有 pending item；所有 admitted item 都必须已有 result_snapshot，即对应 generation 的处理已终态、delete 已 completed / not_required，且成功项 QA 已终态。
  • finalizer 在同一事务只聚合 item 快照、写 final_counts 与 counts_frozen_at，再把 bulk run 改为 completed；PV/PVC GC 与云同步不属于该批次。
  • canceled / failed 批次进入终态时也必须执行同一个 finalizer；事务失败则保持非终态并重试，不能出现“已完成但没有固化计数”。
  • 批次终态后的汇总读取 final_counts，逐条历史读取 items，不再依赖可覆盖的 Derivative 归属字段。
  • 取消先把 bulk run 置为 cancel_requested 并原子写 materialized_at 关闭后续物化；pending item 的 admission_status 置 canceled，已 admitted item 设置 Derivative cancel request。
  • 取消不会回滚已经成功的派生结果，也不会影响手动云同步。

派生质检与云同步

双目拆分自动 QA

  1. manifest 的 kind、generation、镜像和源身份正确。
  2. 输出对象存在、大小匹配，MCAP 头尾 magic 有效。
  3. 左右图像 topic 存在、数量为正且相等。
  4. IMU 数量为正；时间戳、duration 与 generation 前缀合理。

处理验证成功时写 qa_status=pending。Reconciler 以条件 UPDATE 领取为 running；若进程崩溃，超过 QA timeout 的 running 会回到 pending 并安全重跑。QA 失败不改变 processing succeeded，也不允许重新双目拆分；管理员只能重新执行 QA。

failed / canceled 的双目拆分没有成功产物，不自动认领 stereo_split；管理员可以明确选择重试处理或手动同步原始文件，Episode 行锁决定唯一结果。processing succeeded 后，无论 QA 状态如何，原始同步都不再允许；QA 失败只能重新 QA。sync log 为 pending / in_progress 或 Episode 已 cloud_synced 后，禁止重新 QA，避免上传期间改变准入事实。

复用一套 Sync Worker

pending sync log
  → read source_snapshot
  → validate source-specific QA gate
  → register/adopt Hilbert rawDataId
  → upload snapshot object
  → update Episode canonical cloud fields

不新增派生 Sync Worker。现有 Worker 的 pending / failed / canceled 恢复全部从 sync log 反序列化 upload input。original 在准入时检查 Episode QA；stereo_split 在准入、claim 和完成事务中检查 Derivative processing succeeded 与 QA approved。Worker不得使用 Episode metadata.object_key 或 episodes.checksum 覆盖派生快照。

第一阶段 KEYSTONE_SYNC_AUTO_SCAN_ENABLED 必须为 false；只恢复已经持久化的 pending / retryable sync log。以后确有自动同步需求时，再基于同一 source snapshot 准入事务开启。

rawData 注册始终写 episodes.hilbert_raw_data_id，完成始终写 Episode 既有 cloud_synced、cloud_synced_at 与 cloud_mcap_path。因此现有列表、统计、状态 API 仍把“Episode 的正式表示已同步”解释为 cloud_synced=true，无需在两张表间猜测。

来源认领是不可逆业务事实，不是临时 worker lease。同步失败、服务重启或 rawDataId 已分配都只能重试同一 source；不得清空字段后改传另一份 MCAP。

Hilbert 注册恢复

Hilbert 对 Episode 的原始 / 派生关系完全无感，不增加字段、表或接口。Keystone 调用现有 rawData register；若出现超时、连接中断或“bagName 已存在”等不确定结果，则调用 Hilbert 现有 rawData query，以 workspace 与冻结的规范 bagName 分页查询，并在客户端筛选完全相等的 bagName。只有 workspace、采集计划、bagName、开始/结束时间、大小和 digest 与冻结注册请求全部一致时，才取回该行 rawDataId；任一字段不同都作为不可重试冲突，禁止覆盖或新建第二条。

该互斥只约束 Hilbert 正式发布：TOS 中仍同时保留不可变原始 MCAP 与双目拆分派生对象，下载、QA 和审计可以访问两者；删除 PV/PVC 或切换页面状态都不会删除任何一份 TOS 数据。

max_concurrent 只允许 1～100，并由单条和所有批次共享。提高后 Reconciler 会立即唤醒并补充任务；降低后不强制终止已运行 Job，只停止提交新 Job，直到活跃数低于新上限。设置更新与 queued / submitting 的 Orbit POST 通过单副本内的 dispatch 锁串行化：PUT 成功返回前会等待已经开始的旧配置提交收敛，返回后不会再发起使用旧上限的新 Job。Keystone 要求镜像使用显式 registry、仓库路径与 @sha256: digest，拒绝 tag-only、隐式 Docker Hub、userinfo 和空仓库，但不限制仓库域名或 namespace。镜像仓库密码、Token 与 Kubernetes imagePullSecret 永不返回或接收于该 API；它们继续由集群运维配置。管理员保存任意合法 digest 就是在授权 Orbit 执行该镜像，必须依靠管理员权限、审计历史与集群镜像拉取策略控制风险。配置冲突返回 409，页面刷新后由管理员重新确认。

系统设置页面是可扩展的前端容器，不是任意 key/value 配置平台。每个新增设置仍需 Keystone 定义字段、权限、校验、生效语义和审计；密钥、集群身份、资源 envelope 与安全边界不开放给浏览器。

设置页不是版本选择器：只能看到当前配置和审计历史，不能让某个 Episode 选择历史镜像，也不提供一键回滚。需要恢复旧 digest 时，管理员重新提交该 digest，形成一条新的审计记录。页面在保存前明确提示：修改会影响尚未冻结的 queued generation，不影响已冻结或已成功的记录。

Keystone

本功能只新增两个 Keystone 环境变量。KEYSTONE_ORBIT_BASE_URL 非空即启用双目拆分，为空即不启动 Manager、API 执行入口和 Reconciler；不再设置独立 feature flag。

变量用途规则
KEYSTONE_ORBIT_BASE_URLOrbit 地址及启用条件例如 http://orbit.archebase-system.svc.cluster.local:8080；非空启用，为空关闭

command、输出文件名、QA 逻辑与运行 envelope 是 Keystone 代码中的固定双目拆分契约：Orbit HTTP 超时 10 秒；requests 为 CPU 2、内存 4 GiB、临时盘 4 GiB；limits 为 CPU 4、内存 8 GiB、临时盘 8 GiB；Job deadline 3600 秒；完成后 TTL 604800 秒；轮询 5 秒；源文件上限 500 GiB；日志尾部 1 MiB。实际镜像 digest 和全局并发始终来自数据库系统设置，初始并发为 1；没有镜像时处理入口不可用。更新设置不创建新业务版本，也不会重新排队 succeeded 数据。

作业镜像只在 Reconciler 首次冻结 queued generation 时读取。冻结后即使管理员再次保存镜像或代码变化，该 generation 的提交与恢复仍使用数据库中的 orbit_request；失败重试的新 generation 才会在首次调度读取当时的当前镜像。全局并发不写入 Job 快照，Reconciler 每次准备提交 queued 任务时读取最新设置。

安全

  • 只有管理员可调用 data-ops 路由；Episode 动作每次重新检查 workspace 权限。镜像设置是全局配置，不属于单个 workspace，只接受现有 admin 身份。
  • 镜像配置接口是集群代码执行边界：复用现有 admin 角色，强制显式 registry 与 digest，并以 append-only 记录审计每次变更；作业 API 不接受镜像字段。Keystone 不限制仓库，管理员保存即授权执行。
  • 双目拆分契约由 Keystone 固定实现；镜像、命令、参数和本地路径取自首次 Reconcile 时的受信配置，TOS URI 只由 Episode metadata 规范化生成。
  • 完整服务端请求先持久化再发送；客户端输入和后续环境配置都不能修改已经冻结的 orbit_request。
  • cloud_publish_source 只能由服务端同步准入事务认领，客户端不能指定、清空或切换；原始手动、管理员批量和派生入口使用相同 Episode 行锁。
  • Orbit 使用 argv，不构造 shell；请求中不出现 AK/SK、STS、签名 URL 或 registry 凭证。
  • Job 只看本地路径；父目录可见性与 write 实际为 read-write 的语义必须计入权限模型。
  • 原始 Episode 对象 key 必须不可覆盖；当前 Orbit / CSI 合约不提供 version ID 绑定退路。
  • 输出前缀按 generation 唯一；随机后缀、实际镜像 digest 和源对象身份随当前请求持久化。

运维观测边界

本期不新增一套双目拆分专用 metrics 与告警平台。运维先使用 Derivative / bulk run 数据库状态、Keystone 日志、Orbit Job 状态和 Kubernetes 既有监控观察队列、失败、ImagePull、CSI、TOS 授权、Orbit DELETE 与孤儿 PV/PVC。

资源积压越过安全阈值时清空 KEYSTONE_ORBIT_BASE_URL 并重新部署 Keystone，以停止接收和调度新的双目拆分任务。专用有界指标与自动告警在确认实际运维阈值后另行实现，不阻塞本期功能。

部署顺序

  1. 在 Keystone jobs/stereo-split/ 增加源码、Dockerfile、测试与独立镜像流水线；Orbit 只负责按冻结请求运行镜像。
  2. 验证 staging TOS CSI、data-binding RBAC、job identity 与 Orbit binding GC。
  3. 启用 Orbit data bindings，配置 TOS endpoint，发布镜像 digest。
  4. 实现镜像配置审计、cloud source 回填、episode_derivatives、bulk_run_items、bulk_runs 字段和 sync_logs.source_snapshot migration。
  5. 验证现有 Hilbert rawData query 可被 Keystone 服务身份调用，并能按 workspace、bagName 分页返回完整注册字段；Hilbert 本身无需部署功能改动。
  6. 修改现有 Sync Worker 从 source snapshot 上传并关闭自动 scanner；再实现固定双目契约、单 Reconciler、批次 Materializer 与 handler。
  7. 实现 Synapse 双目拆分面板与批量入口；在 staging 完成端到端与容量测试。
  8. 生产准备 CSI、RBAC、identity、Orbit binding GC、孤儿资源告警与镜像；先应用数据库 migration。
  9. Keystone以拒绝新处理的状态上线，确认所有旧 Pod 已退出且新 Sync Worker 已遵守来源锁，再部署 Synapse。
  10. 启用双目拆分，以一个 canary Episode 和小并发开始，随后逐步放量。

第二种处理功能出现时

  1. 先实现第二种功能的固定请求、验证和 QA，并提供确定性样例与容量数据。
  2. 只有两个实现出现稳定共同点时，才抽取薄 Processor interface。
  3. 继续复用 Derivative、bulk items 和 Reconciler；真实输出差异放入 result JSON。

本期不为尚不存在的第二种功能提前编码。只有输出差异无法容纳于固定列和 result JSON 时，才重新评估数据模型。

回滚

  • 先停止接收新处理，继续运行 Materializer finalizer、Reconciler、Sync Worker 与集群 GC。
  • 只有明确回滚决策时才停止活跃 Job；每个终态 Job 都必须显式删除。
  • 只要存在任意活跃或 succeeded Derivative、stereo_split source claim 或派生 pending sync log，就不能运行不识别这些事实的旧 Keystone。
  • 必须回滚时，先关闭所有旧版原始手动、批量和自动同步入口，再启动旧服务；否则它可能上传原始 MCAP。
  • 回滚前必须清点所有活跃 Job、pending sync log 与来源认领；任何回滚都不得清空或改写已认领来源和 rawDataId。
  • generation 前缀不可变；只删除超过安全窗口、无当前成功引用的残缺前缀。
  • 任何回滚和清理都不得触碰原始 Episode MCAP。

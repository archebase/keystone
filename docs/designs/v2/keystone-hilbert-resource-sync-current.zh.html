核心判断

“同步资源”不是一个统一定时任务，而是职责、频率和失败边界不同的两条主链路。

PRIMARY CONCLUSION 先投影执行资源，再同步计划并补齐任务；Workspace 资源不周期刷新，dc_plan 每 5 分钟刷新。

01

总体链路

Server 启动时按固定顺序执行 Workspace 同步、dc_plan 同步，再启动 dc_plan 周期任务。前一阶段失败不会阻止后一阶段继续尝试。

A / Workspace 资源投影STARTUP + MANUAL
A1
确保默认 Workspace

创建或恢复本地 workspaces.id=0，它不参与 Hilbert 计划同步。

A2
拉取可见 Workspace

通过 Digest AK/SK 调用 list-available，可见范围由 Hilbert 账号权限决定。

A3
事务 Upsert Workspace

先整批校验，再在一个事务中写入 workspaces。

A4
逐 Workspace 投影资源

Admins/Members → data_collectors；DC Devices/Types → robots。

B / 计划与任务投影STARTUP + 5 MIN + MANUAL
B1
读取本地 Hilbert Workspace

只处理 source='hilbert'、未删除且 ID > 0 的 Workspace。

B2
分页拉取 dc_plan

每页 200，直到达到 total 或返回空页。

B3
事务 Upsert 计划

校验计划归属与必填字段，整批写入当前 Workspace 的 dc_plan。

B4
按计划补齐任务

解析 collector、robot、workstation，并补到 target_count。

启动顺序：syncWorkspacesOnStartup() → syncDCPlansOnStartup() → startPeriodicDCPlanSync()。Workspace 同步失败时只记录日志，dc_plan 仍会基于数据库里已有的 Hilbert Workspace 继续同步。

02

Workspace 资源同步

入口是 WorkspaceSyncService.Sync。它先保证本地默认空间，再写 Workspace 主表，最后为每个 Hilbert Workspace 单独同步人员与机器人。

配置门禁

必须同时具备数据库、Hilbert BaseURL、AccessKey、SecretKey，并且 Hilbert client 报告 Digest 服务认证可用；否则启动同步跳过，手动接口返回 503。

确保默认 Workspace

Keystone 固定维护 id=0、source='default' 的本地兜底空间。逻辑先 UPDATE 恢复软删除记录；若 MySQL 报告 0 行变化，会再次确认主键是否存在，避免重复插入 0。

拉取与校验可见 Workspace

调用 Hilbert /v1/console/workspace/list-available。要求 ID > 0、名称非空、返回列表中 ID 不重复；任一记录非法，整批 Workspace 不写入。

事务写入 Workspace

整批 Workspace 在一个数据库事务中 Upsert。Hilbert ID 直接作为本地主键；同步 name、description、admins、members、Hilbert 创建/更新时间和原始同步时间；重复记录会恢复 deleted_at=NULL。

排除服务身份

人员投影前，先把配置中的 AccessKey 和 GET /account/get-cur 返回的当前账号 code 加入排除集合，避免 Keystone 的 Hilbert 服务账号被当成数采员。查询当前账号失败只告警，不中止同步。

逐 Workspace 同步人员与机器人

每个 Workspace 开独立事务。人员来自 admins + members 去重列表；机器人来自该 Workspace 的全部 dc-device。不同 Workspace 互相隔离，一个失败不回滚已完成的其他 Workspace。

人员 → data_collectors

  • 逐 code 调用 Hilbert account query，pageSize=1。
  • account.code → data_collectors.operator_id。
  • displayName 为空时回退到 code。
  • metadata 保存 Hilbert account ID、角色、外部用户类型、状态和 last_seen_at。
  • 若同 operator_id 已存在且 metadata source 不是 hilbert，拒绝覆盖并记录错误。
  • 软删除记录可被 Upsert 恢复；更新已有记录时当前代码不强制改写 status。

设备 → robots

  • 每个 Workspace 调用一次 dc-device query，使用 pageSize=-1。
  • Hilbert device 数字 ID 转字符串 → robots.device_id。
  • device.name → robots.device_name；Workspace ID 直接写入。
  • 每台设备按 type ID 单独查询设备类型，名称写入 device_type。
  • 若同 device_id 是非 Hilbert 本地资源，拒绝覆盖。
  • 若机器人已有 current workstation 且属于另一 Workspace，拒绝迁移 Workspace。
03

dc_plan 与任务生成

dc_plan 同步只依赖本地已经存在的 Hilbert Workspace。计划成功落库后，任务生成按 plan 独立执行；生成失败不会回滚计划投影。

APPROVED REVISION / NOT IMPLEMENTED YET 本节记录的是当前代码行为。已确认的目标方案将移除同步后的批量 task generation，改为进入数采页刷新计划、准备时按需创建下一条 task。 
for workspace in local workspaces where source = "hilbert":
    plans = fetch Hilbert dc_plan pages(pageSize=200)
    validate every plan
    transaction: upsert all plans for this workspace

    for plan in plans:
        transaction:
            lock plan
            collector = data_collectors[operator]
            robot = robots[str(dc_device_id)]
            workstation = find or create(robot, collector, workspace)
            missing = target_count - existing_non_deleted_tasks
            create missing pending tasks

计划校验与写入

  • Workspace 必须是未删除的 Hilbert 投影，默认 Workspace 0 被明确拒绝。
  • 计划 ID、Workspace 归属、名称、operator、dc_type、创建人、日期和数值字段均校验。
  • 同一批返回的 plan ID 不允许重复。
  • 本地已有同 plan ID 但属于另一 Workspace 时，整批事务失败。
  • 保存 Hilbert 原始 JSON 到 raw_payload，便于追溯。
  • Hilbert 本次未返回的本地计划不会删除或软删除。

任务补齐规则

  • collector 按 plan.operator 匹配，并验证其 Workspace 访问权。
  • robot 按 str(plan.dc_device_id) 匹配，并要求 workspace_id 一致。
  • 优先复用同 robot + collector + workspace 的工位；历史 superseded 工位会被重新激活为 offline。
  • 找不到工位时自动创建，初始 status='offline'、is_current=false。
  • 只补齐 target_count - existing_count；target 减少时不删除任务。
  • 新任务状态为 pending，dc_plan_id 指向 Hilbert plan，local_dc_plan_id=NULL。

幂等边界：计划 Upsert 是幂等的；任务生成按所有未软删除任务计数，不区分 pending / uploading / completed。重复同步不会重复创建，只有 Hilbert target_count 增大时才补缺口。

05

事务与失败隔离

当前实现不是“全部成功或全部失败”。不同层级采用不同事务边界，以允许局部资源继续同步。

阶段事务边界失败后行为是否继续
默认 Workspace单条 UPDATE / 查询 / INSERT失败则整个 Workspace Sync 返回失败Server 仍继续尝试启动 dc_plan 同步
Workspace 主表本次 Hilbert 返回的全部 Workspace 共用一个事务任一校验或 Upsert 失败，不提交任何 Hilbert Workspace不进入资源投影
人员 + 机器人每个 Workspace 一个事务单个人员/机器人错误通常记录并跳过；设备列表查询失败会回滚该 Workspace 内已经写入的人员继续下一个 Workspace
dc_plan每个 Workspace 的全部计划一个事务该 Workspace 计划不提交SyncAllWorkspaces 继续其他 Workspace
Task generation每个 plan 一个独立事务返回 blocked reason；该 plan 不创建任务其他 plan 继续，dc_plan 同步本身仍视为成功

结构性错误：直接失败

  • Hilbert 不可达、Digest 认证失败或响应 code 非 0。
  • Workspace / plan 返回记录不合法或重复。
  • Workspace 主表、dc_plan 主表事务失败。
  • 上下文超时；默认 5 秒覆盖一次完整同步调用。

业务缺口：记录后继续

  • Workspace 成员账号不存在或查询失败。
  • 机器人类型查询失败、资源来源冲突、Workspace 绑定冲突。
  • plan 缺 collector、robot、Workspace 权限或工位创建失败。
  • 这些错误会进入 summary / 日志，但不必然让外层 HTTP 请求失败。

07

当前边界与风险

以下是代码当前真实行为。它们不一定都是缺陷，但会直接影响同步一致性、性能和运维预期。

一致性边界

  • 只 Upsert，不做删除收敛：Hilbert 删除 Workspace、成员、设备或计划后，本地对象不会自动软删除。
  • 资源不周期刷新：人员或设备变更只有重启 Keystone 或手动 Workspace Sync 才能看到。
  • 状态字段保守：collector / robot 已存在时 Upsert 不强制把 status 改回 active。
  • 计划与资源可能错位：Workspace 启动同步失败后，dc_plan 仍可能基于旧资源继续拉取和生成。

性能与容量边界

  • 账号 N+1：每个去重后的 admin/member 各发一次 account query。
  • 类型 N+1：每台带 type ID 的设备各发一次类型查询，没有本次同步级缓存。
  • 设备一次性拉全：pageSize=-1，依赖 Hilbert 支持无限页语义。
  • 共享超时：一次全量同步共享默认 5 秒 context；Workspace 多、成员多或 plan 分页多时容易整体超时。

任务生成边界

  • 只根据 target_count 补任务，不根据 cur_count 回收或完成任务。
  • 已有任务使用旧 metadata；同步计划不会刷新已生成任务快照。
  • 自动创建的 workstation 是 offline 且非 current，后续仍需运营侧分配/激活流程。
  • task generation blocked 不会使 dc_plan 同步 HTTP 失败，需要查看响应 summary。
  • 目标改造：每计划最多一条 pending；target 增减只影响后续供应，ready 及以后快照不变。

运维检查重点

  • Keystone 与 Hilbert 时钟必须同步，Digest 使用毫秒时间戳。
  • AK 所属账号必须能看见目标 Workspace，并具备相关查询权限。
  • 关注日志中的 workspace 级 errors 与 task generation blocked reason。
  • 资源变化后，先触发 Workspace Sync，再触发 dc_plan Sync，顺序不能反。

最终结论 / CURRENT IMPLEMENTATION

Hilbert 负责主数据与计划定义；Keystone 负责受控投影、运行时绑定和本地执行状态。当前代码仍批量生成 task；已确认的下一步是把 task 供应收缩到准备时按需创建。

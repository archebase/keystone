00

核心判断

本设计解决的核心矛盾是：尽量不改变 ego-portal-lite 和 data-sdk，同时让 Keystone 接住上传控制面。

方案 A 的成功定义：文件实际落在阿里云 OSS；Keystone 负责发放上传会话、签发临时 STS、接收 CompleteUpload，并记录可追踪日志。

这不是把文件写入 Keystone 当前 MinIO/S3 的方案。data-sdk 的数据面使用 AlibabaCloudOSS Swift SDK，第一版不改 SDK，因此 Keystone 不能把 MinIO 当成目标数据面。Keystone 在本方案中是 data-platform SDK-facing gRPC API 的兼容实现。

01

背景与问题

ego-portal-lite 已经集成 data-sdk；Keystone 现有上传链路面向 axon_transfer 和 MinIO，两者协议不同。

现有移动端链路

  • App 调用 QiongcheDataGatewaySDK.saveConfigAndInit 完成设备初始化。
  • App 创建 DataGatewayClient.fromArchebaseConfig。
  • App 调用 client.uploadEvents(request) 上传 capture.mcap。
  • 控制面是 gRPC；数据面是 Alibaba OSS SDK。

现有 Keystone 链路

  • Keystone 通过 WebSocket 通知 axon_transfer。
  • axon_transfer 上传文件到 MinIO/S3。
  • Keystone 校验上传对象后推进 task 状态。
  • 这条链路不是 data-sdk 期望的 public gRPC control plane。

因此，第一版不尝试改造 Keystone 现有 Axon 上传链路，也不让 data-sdk 写 Keystone REST 接口；而是在 Keystone 里增加一个隔离的兼容层。

02

目标与非目标

范围必须收紧：先让链路可运行、可观察、可验收，再决定是否产品化。

类型 内容
目标 Keystone 监听 data-sdk 需要的三个 gRPC 端口：50051、50053、50057。
目标 Keystone 用阿里云 STS AssumeRole 生成临时 OSS 上传凭证，并返回给 iOS SDK。
目标 ego-portal-lite 只改 base URL；业务上传逻辑和 data-sdk 不改。
目标 Keystone 收到 CompleteUpload 后打印完整非敏感 metadata 日志。
非目标 不把对象落到 Keystone MinIO；不改 data-sdk 数据面；不接入 Keystone 现有 task 表。
非目标 第一版不做 TLS、不做入库、不做 OSS HeadObject 校验、不做跨进程持久化恢复。
03

方案总览

Keystone 新增一个独立兼容包，向外呈现 data-platform 的 SDK-facing API。

InitDeviceApp 通过 50057 初始化设备，Keystone 返回 dummy api_key 和 tags。
ExchangeSDK 通过 50051 换 token，Keystone 直接放行。
CreateSDK 通过 50053 创建 logical upload，Keystone 生成 object key。
STSKeystone AssumeRole，返回 OSS 临时凭证。
CompleteiOS 直传 OSS 后回调 Keystone 完成上传。
ego-portal-lite
  -> DeviceInitService.InitDevice        :50057
  -> AuthService.ExchangeCredential      :50051
  -> DataGatewayService.CreateLogicalUpload :50053
  -> AlibabaCloudOSS multipart/put object
  -> DataGatewayService.CompleteUpload   :50053

Keystone 兼容层只通过 `main.go` 启停，与现有 Axon transfer、MinIO、REST API 低耦合。

04

模块边界

兼容层作为独立 POC 包存在，避免污染 Keystone 当前上传模型。

keystone/internal/services/dgwcompat/
  config.go
  server.go
  auth_service.go
  device_init_service.go
  gateway_service.go
  sts_client.go
  object_key.go
文件 职责
config.go 从环境变量读取 compat 配置，不接 Keystone 全局 config loader。
server.go 启动和关闭三个 plaintext gRPC server。
auth_service.go 实现认证放行，返回 dummy bearer token。
device_init_service.go 实现设备初始化，返回 dummy api_key 和基础 tags。
gateway_service.go 管理内存 upload session，处理 create/reissue/recovery/abort/complete。
sts_client.go 手写最小阿里云 STS AssumeRole HTTP 调用；另支持 mock STS。
object_key.go 生成安全、可读、低冲突的 OSS object key。
05

gRPC 合约

Keystone 需要补齐 DeviceInitService 的 Go 生成代码，并实现 data-sdk 会调用的方法。

AuthService :50051

ExchangeCredential 接受任意 credential，返回非空 access token、token type、过期时间。

DeviceInitService :50057

InitDevice 和 ReinitDevice 都返回 dummy api_key。tags 至少包含 device_id 和 source。

DataGatewayService :50053

CreateLogicalUpload 创建内存 session，生成 OSS key，返回 STS 凭证。

Recovery RPC

GetUploadRecovery、ReissueUploadCredentials、AbortUpload 做最小兼容，支持进程内恢复。

UploadCredentials {
  bucket: OSS_BUCKET
  endpoint: OSS_PUBLIC_ENDPOINT
  object_key: ego-portal-lite/{device_id}/{capture_id}/{upload_id}/capture.mcap
  sts_access_key_id: AssumeRole result
  sts_access_key_secret: AssumeRole result
  sts_security_token: AssumeRole result
  sts_expire_at_unix: AssumeRole expiration
  part_size_bytes: KEYSTONE_DGW_UPLOAD_PART_SIZE_BYTES
}
06

配置与部署

POC 重新部署专用 OSS bucket 和 RAM Role，不复用 data-platform 现有云资源。

KEYSTONE_DGW_COMPAT_ENABLED=true
KEYSTONE_DGW_AUTH_ADDR=:50051
KEYSTONE_DGW_GATEWAY_ADDR=:50053
KEYSTONE_DGW_DEVICE_INIT_ADDR=:50057

KEYSTONE_DGW_OSS_BUCKET=archebase-keystone-poc
KEYSTONE_DGW_OSS_PUBLIC_ENDPOINT=https://oss-cn-shanghai.aliyuncs.com
KEYSTONE_DGW_OSS_KEY_PREFIX=ego-portal-lite
KEYSTONE_DGW_UPLOAD_PART_SIZE_BYTES=8388608

KEYSTONE_DGW_STS_ROLE_ARN=acs:ram::ACCOUNT_ID:role/keystone-ego-upload-role
KEYSTONE_DGW_STS_SESSION_TTL_SECONDS=3600
KEYSTONE_DGW_ALIBABA_CLOUD_ACCESS_KEY_ID=...
KEYSTONE_DGW_ALIBABA_CLOUD_ACCESS_KEY_SECRET=...
KEYSTONE_DGW_ALIBABA_CLOUD_STS_REGION=cn-shanghai
KEYSTONE_DGW_ALIBABA_CLOUD_STS_ENDPOINT=https://sts.cn-shanghai.aliyuncs.com

KEYSTONE_DGW_MOCK_STS=false

第一版使用 plaintext gRPC。ego-portal-lite 的 base URL 使用 http scheme，SDK 会根据 scheme 选择明文连接，并按固定端口访问三个服务。

07

对象命名与状态

object key 由 Keystone 生成，不信任客户端路径；状态只保存在进程内。

ego-portal-lite/{device_id}/{capture_id}/{upload_id}/capture.mcap
  • device_id 从 client_hints["device_id"] 取，缺失为 unknown-device。
  • capture_id 从 client_hints["capture_id"] 取，缺失为 unknown-capture。
  • upload_id 使用 UUID，避免覆盖。
  • path segment 只保留字母、数字、-、_、.；其他字符替换成 _。
  • 第一版重启丢失 session 可以接受；客户端会重新上传。
08

权衡与风险

本方案有意牺牲产品化完整性，换取最低改动的链路验证。

风险 影响 缓解
不入库 Keystone 重启后无法恢复 upload session。 第一版接受；后续再设计 upload_attempt 表或复用正式数据模型。
不 HeadObject Keystone 无法判断对象是否真的存在。 验收时人工在 OSS 控制台或 ossutil 检查；日志作为控制面证据。
plaintext gRPC 不适合公网长期运行。 仅用于 POC；链路通过后补 TLS、证书、SNI 和 iOS 信任链。
手写 STS 客户端 签名和 XML 解析可能出错。 参考 data-platform Rust 实现和 Keystone 现有 OSS 签名代码；补单元测试。
专用 RAM 权限过宽 POC bug 可能写入非预期路径。 Role policy 限制到专用 bucket 和 ego-portal-lite/* prefix。
09

实施计划

按垂直链路拆分，先让 gRPC 合约打通，再接真实 OSS STS。

  1. 同步 proto：把 DeviceInitService 相关定义加入 Keystone proto，并运行 make proto。
  2. 新增 dgwcompat 包：实现配置读取、三个 gRPC server、内存 session store。
  3. 实现 mock STS：先用本地测试覆盖 CreateLogicalUpload 和 ReissueUploadCredentials。
  4. 实现真实 STS：手写最小 AssumeRole，解析 XML 凭证和 expiration。
  5. 接入 main.go：按 KEYSTONE_DGW_COMPAT_ENABLED 启停 compat server。
  6. 小改 ego-portal-lite：只切换 DataGatewayUploadService.endpoint 到 Keystone POC host。
  7. 联调验收：iOS 端收到 completed，Keystone 日志出现 completion，OSS 中能看到对象且大小一致。
10

验收标准

第一版验收以端到端上传完成和 OSS 可见对象为准。

  • ego-portal-lite 上传流程不改调用方式，只替换 base URL。
  • iOS 端 uploadEvents 收到 .completed。
  • Keystone 日志出现 CompleteUpload 成功记录，包含 upload id、logical upload id、bucket、object key、file size、capture id、task id、device id。
  • 日志不包含 STS secret、STS token、长期 AK/SK。
  • OSS 控制台或 ossutil 可见对象，key 符合约定，size 与本地 capture.mcap 一致。
决议状态：方案 A 已收敛。文件落阿里云 OSS；Keystone 实现兼容控制面；不改 data-sdk；第一版不入库、不做 HeadObject、不做 TLS。

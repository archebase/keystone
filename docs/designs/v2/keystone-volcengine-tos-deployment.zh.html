Deployment Design / Volcengine TOS

Keystone接入 TOS部署设计

用两级最小权限把长期身份压缩成单对象、短时效的上传与 QA 读取凭据。

01 / LONG-LIVED 运行 IAM 用户 只允许 AssumeRole
02 / COMPRESS STS 双角色 上传与读取分离
03 / TARGET 私有 TOS 对象 单 bucket / 单 prefix

长期 AK/SK 不直接读写 TOS；它只负责扮演两个受限 Role，Keystone 再用 Session Policy 把每次凭据压缩到单个对象。

01

目标与边界

本文说明全新部署 Keystone 并启用火山引擎 TOS 时，云上必须创建的资源、推荐的最小权限策略、CLI 创建顺序，以及每项资源在 .env 中的对应配置。

本次覆盖

  • 设备通过 Keystone 获取短期 STS，直传单个 TOS 对象。
  • Keystone 使用独立只读 Role 对 MCAP 做 QA Range Read。
  • 运行 IAM 用户、Role、Policy、Bucket、AK/SK 与环境变量。
  • 创建后的权限核验、部署验收和安全回滚。

不在范围

  • Hilbert 服务、MySQL、MinIO 的部署。
  • 已有 TOS 数据迁移和历史 multipart 会话恢复。
  • 浏览器直传所需 CORS；当前数据面是原生 Swift SDK。
  • 把管理员或 root AK/SK 放入 Keystone 运行环境。

04

创建前准备

以下命令以 zsh/bash、火山引擎 CLI ve、tosutil 和 jq 为例。管理员 profile 仅用于建资源，不得用于运行 Keystone。

Deployment parameters
KEYSTONE_ADMIN_PROFILE=iam-admin-audit
KEYSTONE_CLOUD_ACCOUNT_ID=2116584179
KEYSTONE_CLOUD_REGION=cn-beijing
KEYSTONE_TOS_ENDPOINT=tos-cn-beijing.volces.com
KEYSTONE_TOS_BUCKET=archebase-keystone-device-upload-${KEYSTONE_CLOUD_ACCOUNT_ID}
KEYSTONE_TOS_PREFIX=device-uploads
KEYSTONE_RUNTIME_USER=keystone-tos-sts
KEYSTONE_UPLOAD_ROLE=keystone-device-upload-role
KEYSTONE_QA_ROLE=keystone-qa-read-role
KEYSTONE_TOSUTIL_CONFIG=/secure/path/tosutil-admin.conf
Verify administrator identity
ve sts GetCallerIdentity \
  ---profile "$KEYSTONE_ADMIN_PROFILE" \
  ---region "$KEYSTONE_CLOUD_REGION"

# 使用交互模式写入独立 tosutil 配置，避免 AK/SK 进入 shell history。
tosutil config -interactive -conf="$KEYSTONE_TOSUTIL_CONFIG"
不要使用 ve configure list 做验收：部分 CLI 版本会明文输出已保存的 AK/SK。使用 GetCallerIdentity 确认身份。
05

资源创建步骤

5.1 创建私有 TOS Bucket

Create and verify bucket
tosutil mb "tos://${KEYSTONE_TOS_BUCKET}" \
  -acl=private \
  -sc=STANDARD \
  -az=single-az \
  -e="$KEYSTONE_TOS_ENDPOINT" \
  -re="$KEYSTONE_CLOUD_REGION" \
  -conf="$KEYSTONE_TOSUTIL_CONFIG"

tosutil ls "tos://${KEYSTONE_TOS_BUCKET}" \
  -e="$KEYSTONE_TOS_ENDPOINT" \
  -re="$KEYSTONE_CLOUD_REGION" \
  -conf="$KEYSTONE_TOSUTIL_CONFIG"

device-uploads 是对象 key prefix，不是独立目录资源，无需提前创建。可选配置生命周期规则，自动清理长期未完成的 multipart；不要自动删除已完成的 MCAP，除非数据保留策略明确要求。

5.2 创建 Keystone 运行 IAM 用户

Create runtime identity
ve iam CreateUser \
  --UserName "$KEYSTONE_RUNTIME_USER" \
  --DisplayName "Keystone TOS STS Runtime" \
  --Description "Runtime identity used by Keystone to assume TOS roles" \
  ---profile "$KEYSTONE_ADMIN_PROFILE" \
  ---region "$KEYSTONE_CLOUD_REGION"

5.3 创建两个 Role 与信任策略

Build trust policy
KEYSTONE_RUNTIME_USER_TRN="trn:iam::${KEYSTONE_CLOUD_ACCOUNT_ID}:user/${KEYSTONE_RUNTIME_USER}"

KEYSTONE_TRUST_POLICY="$(jq -cn \
  --arg principal "$KEYSTONE_RUNTIME_USER_TRN" \
  '{Statement:[{Effect:"Allow",Action:["sts:AssumeRole"],Principal:{IAM:[$principal]}}]}')"
Create upload and QA roles
ve iam CreateRole \
  --RoleName "$KEYSTONE_UPLOAD_ROLE" \
  --DisplayName "Keystone Device Upload Role" \
  --Description "Temporary TOS upload role assumed by Keystone" \
  --MaxSessionDuration 3600 \
  --TrustPolicyDocument "$KEYSTONE_TRUST_POLICY" \
  ---profile "$KEYSTONE_ADMIN_PROFILE" \
  ---region "$KEYSTONE_CLOUD_REGION"

ve iam CreateRole \
  --RoleName "$KEYSTONE_QA_ROLE" \
  --DisplayName "Keystone QA Read Role" \
  --Description "Temporary TOS read role used for MCAP QA checks" \
  --MaxSessionDuration 3600 \
  --TrustPolicyDocument "$KEYSTONE_TRUST_POLICY" \
  ---profile "$KEYSTONE_ADMIN_PROFILE" \
  ---region "$KEYSTONE_CLOUD_REGION"

5.4 创建四个最小权限 Policy

Build policy documents
KEYSTONE_UPLOAD_ROLE_TRN="trn:iam::${KEYSTONE_CLOUD_ACCOUNT_ID}:role/${KEYSTONE_UPLOAD_ROLE}"
KEYSTONE_QA_ROLE_TRN="trn:iam::${KEYSTONE_CLOUD_ACCOUNT_ID}:role/${KEYSTONE_QA_ROLE}"
KEYSTONE_TOS_RESOURCE="trn:tos:::${KEYSTONE_TOS_BUCKET}/${KEYSTONE_TOS_PREFIX}/*"

KEYSTONE_ASSUME_UPLOAD_POLICY="$(jq -cn --arg resource "$KEYSTONE_UPLOAD_ROLE_TRN" \
  '{Statement:[{Effect:"Allow",Action:["sts:AssumeRole"],Resource:[$resource]}]}')"

KEYSTONE_ASSUME_QA_POLICY="$(jq -cn --arg resource "$KEYSTONE_QA_ROLE_TRN" \
  '{Statement:[{Effect:"Allow",Action:["sts:AssumeRole"],Resource:[$resource]}]}')"

KEYSTONE_UPLOAD_TOS_POLICY="$(jq -cn --arg resource "$KEYSTONE_TOS_RESOURCE" \
  '{Statement:[{Effect:"Allow",Action:[
    "tos:PutObject","tos:CreateMultipartUpload","tos:UploadPart",
    "tos:CompleteMultipartUpload","tos:AbortMultipartUpload",
    "tos:ListParts","tos:HeadObject"
  ],Resource:[$resource]}]}')"

KEYSTONE_QA_TOS_POLICY="$(jq -cn --arg resource "$KEYSTONE_TOS_RESOURCE" \
  '{Statement:[{Effect:"Allow",Action:["tos:GetObject"],Resource:[$resource]}]}')"
Create custom policies
ve iam CreatePolicy \
  --PolicyName keystone-assume-upload-role-policy \
  --Description "Allow Keystone runtime to assume only the upload role" \
  --PolicyDocument "$KEYSTONE_ASSUME_UPLOAD_POLICY" \
  ---profile "$KEYSTONE_ADMIN_PROFILE" ---region "$KEYSTONE_CLOUD_REGION"

ve iam CreatePolicy \
  --PolicyName keystone-assume-qa-read-role-policy \
  --Description "Allow Keystone runtime to assume only the QA read role" \
  --PolicyDocument "$KEYSTONE_ASSUME_QA_POLICY" \
  ---profile "$KEYSTONE_ADMIN_PROFILE" ---region "$KEYSTONE_CLOUD_REGION"

ve iam CreatePolicy \
  --PolicyName keystone-device-upload-tos-policy \
  --Description "Allow device sessions to upload below the configured TOS prefix" \
  --PolicyDocument "$KEYSTONE_UPLOAD_TOS_POLICY" \
  ---profile "$KEYSTONE_ADMIN_PROFILE" ---region "$KEYSTONE_CLOUD_REGION"

ve iam CreatePolicy \
  --PolicyName KeystoneTOSQAReadPolicy \
  --Description "Allow Keystone QA to range-read uploaded MCAP objects" \
  --PolicyDocument "$KEYSTONE_QA_TOS_POLICY" \
  ---profile "$KEYSTONE_ADMIN_PROFILE" ---region "$KEYSTONE_CLOUD_REGION"

5.5 绑定 Policy

Attach policies
ve iam AttachUserPolicy \
  --UserName "$KEYSTONE_RUNTIME_USER" \
  --PolicyName keystone-assume-upload-role-policy --PolicyType Custom \
  ---profile "$KEYSTONE_ADMIN_PROFILE" ---region "$KEYSTONE_CLOUD_REGION"

ve iam AttachUserPolicy \
  --UserName "$KEYSTONE_RUNTIME_USER" \
  --PolicyName keystone-assume-qa-read-role-policy --PolicyType Custom \
  ---profile "$KEYSTONE_ADMIN_PROFILE" ---region "$KEYSTONE_CLOUD_REGION"

ve iam AttachRolePolicy \
  --RoleName "$KEYSTONE_UPLOAD_ROLE" \
  --PolicyName keystone-device-upload-tos-policy --PolicyType Custom \
  ---profile "$KEYSTONE_ADMIN_PROFILE" ---region "$KEYSTONE_CLOUD_REGION"

ve iam AttachRolePolicy \
  --RoleName "$KEYSTONE_QA_ROLE" \
  --PolicyName KeystoneTOSQAReadPolicy --PolicyType Custom \
  ---profile "$KEYSTONE_ADMIN_PROFILE" ---region "$KEYSTONE_CLOUD_REGION"

5.6 最后创建运行 Access Key

Create runtime AK/SK once
ve iam CreateAccessKey \
  --UserName "$KEYSTONE_RUNTIME_USER" \
  ---profile "$KEYSTONE_ADMIN_PROFILE" \
  ---region "$KEYSTONE_CLOUD_REGION"
该命令会返回敏感 AK/SK，Secret Key 通常只显示一次。立即写入秘密管理系统；不要粘贴到聊天、工单、Git、日志或共享终端记录。
06

权限边界

身份/会话 允许 明确不允许 资源范围
运行 IAM 用户 对两个指定 Role 执行 sts:AssumeRole 直接 Get/Put TOS；枚举 IAM；扮演其他 Role 两个精确 Role TRN
上传 Role Put、Create/Upload/Complete/Abort Multipart、ListParts、Head GetObject、ListBucket、DeleteObject、访问其他 prefix 指定 bucket 的 device-uploads/*
QA Role tos:GetObject，包含 Range GET 上传、删除、列桶、读取其他 prefix 指定 bucket 的 device-uploads/*
单次 STS Session 本次 object key 所需操作 同 prefix 下的其他对象 Keystone 动态生成的单对象 TRN

Keystone 的上传 Session Policy 在 internal/services/dgwcompat/sts_client.go 中生成；QA Session Policy 在 internal/api/handlers/episode_qa_tos.go 中生成。云上 Role Policy 给出 prefix 上限，应用 Session Policy 再缩到单对象。

8.2 部署验收标准

  • 用运行 AK/SK 调用 sts:GetCallerIdentity，身份是 keystone-tos-sts，不是 root。
  • Keystone 启动时 DGW 配置校验通过，gRPC 服务监听预期端口。
  • 小文件通过 PutObject 上传成功，对象 key 位于 device-uploads/*。
  • 大文件 multipart 可创建、上传分片、ListParts、完成；取消时可 Abort。
  • 上传会话不能 GetObject，也不能访问同 prefix 下的另一个对象。
  • QA 会话可以 Range Get 本次 MCAP，但不能 PutObject 或读取另一个对象。
  • Keystone、设备和日志中均不出现长期 SK、Session Token 或完整临时 AK。
09

风险与回滚

关键风险

  • 把 root/admin AK 写入 .env，导致运行面权限失控。
  • Role Resource 写成 *，绕过 bucket/prefix 隔离。
  • 上传与 QA 共用 Role，使设备获得读取能力。
  • Bucket 地域、Endpoint 和签名 Region 不一致。
  • 日志或 CLI 命令把 AK/SK 暴露到历史记录。

回滚顺序

  1. 先停用或轮换运行 IAM 用户的 Access Key，停止新 STS 签发。
  2. 关闭 KEYSTONE_DGW_COMPAT_ENABLED 并停止设备上传入口。
  3. 确认已完成对象的保留与迁移策略，不直接删除 bucket。
  4. 依次解绑用户/Role Policy，再删除 Policy、Role 和 IAM User。
  5. 只有确认数据可删除或已迁移后，才清空并删除 TOS Bucket。
最终部署判断 云上边界固定为“一桶、一用户、双角色、四策略”；运行用户只有 AssumeRole，上传与 QA 权限分离，Session Policy 每次再收窄到单对象。任何更宽授权都应视为部署偏差。

KEYSTONE / HILBERT / SERVICE AUTH

Hilbert
Digest AK/SK
接管服务认证

删除 Keystone 伪管理员账号登录链路，所有服务到 Hilbert 的后台调用统一使用正式 Digest AK/SK。

核心判断 Keystone 不再保存 Hilbert 账号密码，也不再为后台任务换取 sessionKey；服务身份由 Hilbert AK/SK 直接证明。
实现边界 数采员交互式登录仍使用 Hilbert code/password；本设计只替换 Keystone 后台服务调用 Hilbert 的认证方式。
01

背景与问题

Keystone 当前通过 KEYSTONE_HILBERT_SERVICE_ACCOUNT_CODE 和 KEYSTONE_HILBERT_SERVICE_ACCOUNT_PASSWORD 登录 Hilbert，拿到 sessionKey 后再用 Authorization: Bearer 调用 workspace、dc-plan、dc-device 和 nonce API。

这个模型本质上是在用一个 Hilbert 管理员或机器账号模拟人工登录。Hilbert 现在已经支持正式 AK/SK Digest 认证，Keystone 应该切换到服务到服务凭证，不再保存可交互登录的密码。

本次不做历史兼容：main-v2 是新部署，旧 code/password 环境变量、配置字段、接口依赖和测试 fixture 应直接删除。
当前链路 问题 目标链路
Keystone 持有 Hilbert code/password 后台服务身份和交互登录身份混在一起，密码生命周期不适合服务调用 Keystone 只持有 Hilbert AK/SK
每条服务链路先 Login 再 Bearer 多一次网络调用，且 sessionKey 不是服务认证的必要中间态 每个 Hilbert 受保护请求直接附带 Digest Authorization
配置名表达“service account password” 容易误导部署人员创建管理员密码并下发给 Keystone 配置名表达正式 AK/SK，和 Hilbert 控制台生成凭证一致
02

目标与非目标

目标

  • 删除 KEYSTONE_HILBERT_SERVICE_ACCOUNT_CODE 和 KEYSTONE_HILBERT_SERVICE_ACCOUNT_PASSWORD。
  • 新增 KEYSTONE_HILBERT_ACCESS_KEY 和 KEYSTONE_HILBERT_SECRET_KEY。
  • Keystone Hilbert client 支持 Digest header 生成，并在后台服务 API 上默认使用。
  • workspace sync、dc-plan sync、DGW device auth 三条链路不再调用 Hilbert login。
  • 日志、错误响应和配置摘要不得输出 SK、Digest 或 nonce randomKey。

非目标

  • 不修改 Hilbert 后端认证协议。
  • 不保留 code/password fallback。
  • 不迁移历史部署配置。
  • 不改变 Synapse 数采员登录表单。
  • 不改变设备 API Key、JWT、TOS STS 的现有安全边界。
03

方案总览

Hilbert 的 Digest 认证格式为 Digest ak;epoch_millis;sha256(sk + "," + epoch_millis)。Hilbert 中间件会用 AK 找到账户、解密 SK、校验时间窗、校验 digest、检查 AK/SK 限速，并继续执行角色权限和 workspace 可见性检查。

配置装填 Keystone 读取 Hilbert BaseURL、AccessKey、SecretKey 和 timeout。
请求蓄力 Hilbert client 在每个受保护请求前生成 epochMillis 和 digest。
Digest 冲刺 请求携带 Authorization: Digest ... 直接访问 Hilbert API。
权限落点 Hilbert 按 AK 所属账号的角色和 workspace 权限返回数据。

注意：当前 Hilbert Digest 不绑定 method、path 或 body，因此 Keystone 不应在本次自行扩展签名口径；否则会与 Hilbert 服务端不兼容。

05

Hilbert Client 设计

internal/auth/hilbert_client.go 保留交互式 Login(ctx, code, password)，因为 Keystone 的 /auth/login 仍需要验证数采员 Hilbert 账号密码。新增服务认证能力时不要删除这条用户登录路径。

拆分原则：用户登录继续走 nonce + cipherDigest；后台服务请求统一走 Digest AK/SK。

Digest header 生成

func (c *HilbertClient) serviceAuthorizationHeader(now time.Time) (string, error) {
    ak := strings.TrimSpace(c.accessKey)
    sk := strings.TrimSpace(c.secretKey)
    if ak == "" || sk == "" {
        return "", ErrHilbertInvalidCredentials
    }

    millis := strconv.FormatInt(now.UnixMilli(), 10)
    digest := sha256.Sum256([]byte(sk + "," + millis))
    return "Digest " + ak + ";" + millis + ";" + hex.EncodeToString(digest[:]), nil
}

请求封装

当前所有需要 Hilbert 服务身份的 client 方法应移除 sessionKey 参数，改成内部自动设置 Digest header。公开方法变为：

ListAvailableWorkspaces(ctx)
QueryDCPlans(ctx, workspaceID, pageNum, pageSize)
QueryAccountByCode(ctx, code)
QueryDCDevices(ctx, workspaceID)
QueryDCDeviceTypeByID(ctx, id)
GetDCDeviceAPIKey(ctx, workspaceID, deviceID)
GenerateDCDeviceAPIKey(ctx, workspaceID, deviceID)
DeleteDCDeviceAPIKey(ctx, workspaceID, deviceID)
ValidateDCDeviceAPIKey(ctx, workspaceID, deviceID, apiKey)
ConsumeNonceWithServiceAuth(ctx, nonceID)

generateNonce 仍可无认证调用；consumeNonce 在 Hilbert 端要求 external_user，因此设备 API Key 获取、生成、校验时消费 nonce 也必须走 Digest。

模块 当前实现 改造后 额外注意

07

权限与安全

Keystone 使用的 Hilbert AK/SK 应属于一个专用 Hilbert 账号。账号角色至少需要满足 external_user，并通过 Hilbert workspace membership 控制可见工作空间。若需要跨所有 workspace 同步，可以使用更高权限账号，但这应是部署决策，不应由 Keystone 代码绕过。

凭证边界

  • SK 只进入环境变量或部署 Secret。
  • Digest header 不写日志。
  • 错误响应只暴露认证失败或 Hilbert 不可用。
  • 配置摘要必须对 SecretKey 使用 json:"-"。

协议边界

  • 不自行把 method/path/body 加入 digest。
  • 依赖 Hilbert 当前 60 秒时间窗。
  • Keystone 机器时钟必须和 Hilbert 保持同步。
  • Hilbert AK/SK 限速会影响批量同步和设备认证峰值。

最终决策

Keystone main-v2 直接切到 Hilbert Digest AK/SK 服务认证。旧的 SERVICE_ACCOUNT_CODE/PASSWORD 不是兼容路径，而是删除对象。交互式账号密码登录只保留在数采员登录场景；所有后台同步和设备认证编排都由 AK/SK 代表 Keystone 服务身份。

  • 部署前在 Hilbert 为 Keystone 专用账号生成 AK/SK。
  • 把该账号加入需要管理的 workspace，优先使用最小可见范围。
  • Keystone 部署 Secret 只写 KEYSTONE_HILBERT_ACCESS_KEY 和 KEYSTONE_HILBERT_SECRET_KEY。
  • 生产验收必须包含真实 Hilbert Digest 调用和设备 API Key 全链路。

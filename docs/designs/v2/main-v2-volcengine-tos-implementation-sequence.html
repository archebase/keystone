在全新生产部署中，直接切断阿里云依赖，并建立 SDK → Keystone → Hilbert 的设备认证链路，再将数据面接入火山云 TOS。

先把 Swift SDK 归并到 Keystone，再打通 Hilbert 设备认证与 Keystone 短期会话；认证主体可信后，才签发 TOS STS 并开放对象上传。

01

范围锁定

本次必须完成

  • Keystone dgwcompat 使用火山云 STS 签发临时凭证。
  • 将原 data-sdk 完整历史导入 keystone/sdk/swift，Keystone 成为唯一源码仓库。
  • Keystone 根目录提供 Package.swift，宿主 App 可通过 Keystone Git URL 引用 SwiftPM package。
  • keystone/sdk/swift 在 iOS 18 / Swift 6 环境直接上传 TOS。
  • Go 与 Swift 从同一份 canonical proto 生成客户端代码。
  • 设备 SDK 只访问 Keystone；Keystone 使用 Hilbert dc-device API 完成初始化、凭证验证和重置。
  • 复用现有设备 auth token 验证首次初始化；token 由管理员签发并绑定设备，不能再只凭 device ID 公开获取。
  • Keystone 签发并统一校验短期设备 JWT，上传身份只能来自 JWT principal。
  • 支持单对象上传、分片上传、凭证刷新、ListParts、HEAD 与 Abort。
  • 协议明确返回并校验 volcengine_tos 和 region。
  • 在 main-v2 全新生产环境使用新 bucket、新 IAM 策略和新部署配置。

明确不做

  • 不迁移阿里云历史对象或数据库记录。
  • 不恢复旧 OSS multipart upload ID。
  • 不支持 App 关闭、崩溃或被系统终止后的跨进程续传。
  • 不长期保留阿里云与火山云双 Adapter。
  • 不兼容旧环境变量或旧版设备 SDK。
  • 不在 Keystone 与原 data-sdk 中长期维护两份 SDK 源码。
  • 不把 Swift package 只放在无法被远程 SwiftPM 直接解析的嵌套目录。
  • 本阶段不修改 Hilbert 源码，不新增 ensure-api-key 或原子 rotate-api-key。
  • 不引入设备证书、mTLS 或自建 PKI。
  • 默认不修改 Keystone 的 MinIO → 云同步客户端，除非 main-v2 同时启用 KEYSTONE_SYNC_ENABLED。
02

目标链路

设备长期身份由 Hilbert 管理，Keystone 负责注册编排、短期设备会话和 TOS 授权。Swift SDK 与 Go 后端进入同一个仓库；设备不直接访问 Hilbert，也不持有 Hilbert 服务账号或火山云长期凭证。

设备初始化 SDK 使用 device ID 与管理员签发的 device auth token 向 Keystone 初始化；Keystone 从 Hilbert 获取或生成设备 API Key。
设备认证 SDK 提交 device ID 与 API Key；Keystone 调用 Hilbert validate，通过后签发带 auth epoch 的短期 JWT。
创建上传会话 Gateway interceptor 校验 JWT principal，Keystone 生成 logical upload、object key 并向火山云 STS AssumeRole。
下发契约 返回 bucket、endpoint、region、临时 AK/SK/token、part size 和 backend。
TOS 数据面 sdk/swift 直接执行 PutObject 或 multipart，并在内存中跟踪分片状态。
密钥边界：设备 API Key 允许进入 Swift SDK，但必须保存在 Keychain；Hilbert 服务账号密钥与火山云长期 AK/SK 永远不得下发。TOS STS 必须限制到目标 bucket 的指定 object-key prefix。
03

设备认证契约

四层凭证

device auth token 同时用于 Recorder WebSocket 和首次 SDK 初始化证明；Hilbert API Key 是 SDK 长期凭证；Keystone JWT 是短期业务会话；TOS STS 只授权本次对象上传。初始化权限在 auth token 上单独记录并一次性消费。

InitDevice(device_id, device_auth_token)
  → device_api_key + authoritative tags

ExchangeCredential(device_id, device_api_key)
  → JWT(device_id, workspace_id, auth_epoch)

CreateLogicalUpload(Bearer JWT)
  → TOS STS(bucket, region, object_key, expiry)
操作 Keystone 编排 失败与重试规则
InitDevice 校验 device auth token 哈希、设备状态和 sdk_initialized_at；调用 query；先 Get，不存在则 Generate Generate 报已存在时回到 Get；成功后消费该 token 的 SDK 初始化权限，但 token 继续用于 Recorder WebSocket
ExchangeCredential nonce/generate；AES-GCM 加密设备 API Key；调用 dc-device/validate；签发短期 JWT Hilbert 不可用时不签发 JWT；不得使用本地静态 Key 或随机假 token 降级
ReinitDevice 正常场景校验当前 JWT；凭证丢失时要求管理员轮换 device auth token 并开启一次 recovery；随后递增 auth_epoch，顺序 Delete、Generate Delete 不存在按成功；Generate 已存在则 Get；同一 recovery 可继续未完成操作；completed 重放只 Get，禁止再次 Delete
Gateway 请求 gRPC interceptor 校验 JWT 签名、过期时间和 auth_epoch device ID、workspace 和对象前缀来自 principal；client hints 只允许校验，不作为身份来源
注册安全门：当前只提交 device ID 的公开 /devices/register 不能继续签发 auth token。token 必须由管理员接口生成并通过可信配置渠道下发；否则攻击者可以自行取得“设备身份证明”。
04

上传契约

现有协议可直接承载

现有 protobuf 已包含 backend 和 region 字段，无需新增 RPC。合仓后应建立一份 canonical proto，同时为 Go 和 Swift 生成代码，并将两个字段提升为运行时必填契约。

UploadCredentials {
  bucket: "main-v2-uploads"
  endpoint: "https://tos-...volces.com"
  object_key: "device-prefix/.../capture.mcap"
  sts_access_key_id: "..."
  sts_access_key_secret: "..."
  sts_security_token: "..."
  sts_expire_at_unix: 178...
  part_size_bytes: 8388608
  object_store_backend: "volcengine_tos"
  object_store_region: "cn-beijing"
}
契约项 Keystone 责任 sdk/swift 责任
object_store_backend 固定返回 volcengine_tos 缺失或不匹配时立即拒绝创建上传会话
object_store_region 从部署配置返回，不从 endpoint 猜测 用于客户端配置和签名；刷新后必须保持不变
临时凭证 AssumeRole，控制 TTL 与最小权限 仅内存使用；到期前刷新；不写日志
ETag 作为存储端返回值记录，不推导阿里云算法 使用 PutObject/CompleteMultipartUpload 返回值并通过 HEAD 对账
part size 下发符合 TOS 限制的固定值 同一上传会话内固定；凭证刷新时不允许变化

认证契约门：升级 device auth token 与 JWT principal

先定义设备身份和凭证生命周期，再修改上传接口。Hilbert dc_device.id 的十进制字符串是唯一 device ID；workspace 必须由 Keystone 投影确定，不能由设备声明。

  • 将现有 ws_client_auth_token 提升为通用 device auth token；仍保存哈希并支持管理员轮换。

  • 明确 API Key 只进入 Keychain；服务账号密钥、nonce random key、JWT、STS 均禁止写日志。

端到端联调：真实设备行为

在预生产 TOS bucket 上验证控制面、数据面和当前进程内的失败处理，而不是只依赖 mock。

  • 首次 Init、重复 Init、错误 device auth token、已撤销 token 和已消费 SDK 初始化权。
  • 错误 API Key 无法换取 JWT；Reinit 后旧 JWT 立即失效。
  • 在 Delete 成功后注入 Generate 失败，使用同一 recovery 操作重试并取得新 Key。
  • 小文件走 PutObject，大文件走 multipart。
  • 当前进程内出现响应不确定或分片重试时，使用 ListParts 对账已成功分片。
  • App 被终止后不恢复旧 multipart；再次上传必须创建新会话。
  • STS 临近过期时刷新客户端并继续同一个 multipart。
  • 上传完成但业务 CompleteUpload 失败时，HEAD 验证后只重试业务完成。
  • 错误凭证、越权 prefix、错误 region 和网络超时均返回可诊断错误。

06

单仓模块责任

Keystone / 控制面

  • 持有 Hilbert 专用机器账号并调用 dc-device API。
  • 管理员签发并轮换 device auth token，分别管理 WebSocket 使用权、SDK 初始化权和恢复授权。
  • 验证设备 API Key，签发 JWT，并通过 auth epoch 撤销旧会话。
  • 持有长期火山云凭证。
  • AssumeRole 并签发短期会话。
  • 生成 object key 和上传会话标识。
  • 保证凭证刷新前后对象定位不变。
  • 记录业务上传完成状态。

Keystone sdk/swift / 数据面

  • 使用 device auth token 初始化，设备 API Key 只保存到 Keychain。
  • 使用 API Key 换取并刷新短期 Keystone JWT。
  • 直接向 TOS 传输文件字节。
  • 在当前上传任务内跟踪 multipart ID、part ETag 和进度。
  • 在凭证过期前调用 Keystone 刷新。
  • 在当前进程内通过 TOS ListParts 处理响应不确定和重试对账。
  • 将 TOS 最终 ETag 回传业务完成接口。
单一来源规则：协议只保留一份 canonical proto；根 Package.swift 负责远程 SwiftPM 解析。Hilbert 保持设备身份权威，Keystone 不复制 API Key 数据库；默认也不修改未启用的 MinIO → 云同步客户端。

08

风险与控制

Swift 客户端适配

火山云官方客户端可能不满足 Swift 6 Sendable、SPM 或流式 InputStream 要求。

控制：Phase 4 作为阻断门；在写正式实现前确定客户端路线。

签名与 region

TOS 的签名、host 形式和 token header 不能沿用 OSS 假设。

控制：region 必须由 Keystone 下发；使用官方客户端或经真桶验证的签名实现。

遗留 multipart

App 被系统终止后无法可靠发送 Abort，已上传分片可能暂时占用存储空间。

控制：显式取消时立即 Abort；生产 bucket 配置未完成 multipart 生命周期清理规则。

权限过宽

设备持有的临时凭证若能列桶或访问其他设备 prefix，会造成跨设备数据暴露。

控制：角色策略限制 bucket、prefix 和必要 multipart 动作；负向权限测试为发布阻断项。

Reinit 非原子窗口

Hilbert Delete 成功而 Generate 暂时失败时，设备在拿到新 Key 前无法进行新认证。

控制：设备级数据库锁、持久化 rotating 状态、同 token 续跑、Generate 已存在时回到 Get。

Hilbert 可用性依赖

Hilbert 不可用时，Init、Reinit 和新的 JWT 交换都会失败。

控制：JWT 保持短期缓存；调用设置超时和有限重试；禁止使用静态 Key 或跳过 validate 降级。

单仓发布风险：SwiftPM 远程依赖默认从仓库根目录读取 manifest，因此 Package.swift 不能只留在 sdk/swift。宿主 App 应固定 Keystone revision 或使用统一 release tag，避免后端与 SDK 版本来源分裂。
09

部署与回滚

部署顺序

先完成 SDK 归并与单仓 CI，再收紧 device auth token 签发并部署 Hilbert 设备认证链路；认证验收通过后准备 TOS 基础设施，并发布依赖 Keystone Git revision 的设备应用。

1归并 SDK 历史并通过单仓 CI
2收紧 device auth token 签发并部署 Hilbert/JWT
3创建 TOS bucket、IAM 与生命周期规则
4App 固定 Keystone Swift package revision
5Init/Reinit + 小文件/大文件 smoke test
6开放设备并归档旧 data-sdk 仓库

回滚原则

在生产验收前保持 Keystone 与 App revision 可回退。如果设备认证、Go 控制面或同仓 Swift SDK 出现阻断问题，停止签发和轮换 device auth token，并停止开放设备，再回退应用或服务版本；已成功写入 TOS 的对象不自动删除。Reinit 已删除旧 Key 时不能通过代码回滚恢复旧 Key，必须继续当前重置状态取得新 Key。

先建立可信设备主体，
再开放对象上传。

完成标准不是“复制了 SDK”或“替换了代码”，而是 Keystone 成为唯一源码与发布入口，设备身份由 Hilbert 验证，Keystone 使用可撤销 JWT 和最小权限 TOS STS 完成可刷新、可校验的大文件上传。

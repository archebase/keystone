01

决策与背景

PR-2 已经把 Hilbert dc_plan 投影到 Keystone。当前实现会在计划同步成功后， 按 target_count - existing_task_count 一次性补齐全部 pending task。 当目标数量较大或 Hilbert 动态调整 operator、device、target_count 时，这种模型会提前制造大量执行实例， 并迫使同步链路承担 task 取消、换绑和迁移责任。

修订后的 PR-3 只保留两个动作：完整刷新 Workspace 的计划投影；在真正准备执行时创建或复用下一条 task。 登录和计划同步不再批量修改 task。方案修订日期：2026-07-21。
当前代码
计划同步后立即按 target_count 补齐全部 task。
目标设计
同步只更新计划；点击准备或完成录制后，才确保存在下一条 task。
执行不变量
pending 可以取消；ready 及以后不随计划变化。
02

目标与非目标

目标

  • Hilbert 始终是计划定义、operator、device 和 target_count 的事实来源。
  • Keystone 持久化 dc_plan 投影，Hilbert 不可用时不影响已准备任务。
  • 进入数采任务页和手动刷新时，通过 Keystone 刷新当前 Workspace 计划。
  • 每个计划最多保留一条未开始的 pending task。
  • task 在准备时创建；进入 ready 后配置快照不可变。

非目标

  • 不把计划刷新做成实时推送或复杂调度系统。
  • 不在登录认证事务中创建、取消或迁移 task。
  • 不修改 ready、in_progress、uploading、completed task。
  • 不因为一次失败或不完整查询删除本地计划。
  • 不把 target_duration 平均分配到单个 task。
  • 不修改 dc_plan.cur_count / cur_duration，保持 Hilbert 投影语义。
03

方案总览

进入数采任务页 / 点击刷新计划
  -> POST /api/v1/operator/plans/refresh
  -> resolve authenticated operator + workspace + robot
  -> fetch complete Hilbert dc_plan snapshot for workspace
  -> validate all pages
  -> transaction:
       mark old Hilbert plans inactive
       upsert returned plans active
  -> return current operator/device plans

点击准备 / 完成录制后自动准备
  -> EnsureNextTask(plan_id, workstation_id)
  -> transaction:
       lock plan
       validate operator / robot / workstation
       reuse existing pending task, or
       create exactly one pending task when target remains
  -> fetch task config
  -> submit Recorder config
  -> task becomes ready and its snapshot is frozen

页面刷新和现有周期同步可以复用同一计划刷新 interface。同步失败时保留本地投影并返回上次同步时间； 只有完整 Workspace 快照成功返回后，才允许把本次未出现的 Hilbert 计划标记为 inactive。

04

计划刷新规则

触发方式

  • 进入数采任务页面时刷新一次，不阻塞登录认证成功。
  • “刷新计划”按钮调用同一个 endpoint，并同步返回刷新后的计划。
  • 现有 5 分钟周期同步可作为兜底，三种触发复用相同实现。
  • 请求 Hilbert 失败时返回本地投影和 last_synced_at，不修改计划状态。

完整快照与本地投影

场景 本地行为 Task 行为
计划新增或字段变化 Upsert dc_plan 投影。 只影响下一条尚未创建的 task。
完整快照中计划缺失 标记 inactive / soft deleted，保留历史。 不再供应下一条；当前执行任务不变。
Hilbert 请求或分页失败 不提交任何投影变化。 已准备任务继续执行。
  • operator 必须来自服务端认证身份，不接受前端提交任意 operator_id。
  • 当前设备先解析为 robots 记录，再用 robots.device_id 对齐 Hilbert dc_device_id。
  • 本地 dc_plan 不允许独立编辑 Hilbert 权威字段。
05

按需 Task 供应

EnsureNextTask 不变量

  • 事务内锁定 plan，并重新读取 target_count 与任务状态计数。
  • 同一计划已有 pending 时直接复用，不能创建第二条 pending。
  • 存在 ready / in_progress 时拒绝准备另一条。
  • 上一条处于 uploading 时允许准备下一条，这是完成录制后自动衔接的预期状态。
  • 可计入目标的 task 数量已经达到 target_count 时返回计划已完成，不创建 task。
  • collector、robot、workspace 或 workstation 不匹配时返回明确业务错误。
  • 新 task 保存当时的 plan 配置快照；进入 ready 后不再受后续同步影响。

目标数量计算

committed = ready + in_progress + uploading + completed

if committed >= target_count:
    cancel existing pending task
    stop supplying tasks
else if pending exists:
    return pending
else:
    create one pending task

cancelled 不计入目标。failed 默认不计入目标，以允许补采；如业务决定失败也消耗目标，应作为独立规则显式配置。

06

Interface 与页面流程

RefreshWorkspacePlans(ctx, workspaceID) ([]DCPlan, error)

EnsureNextTask(ctx, planID, workstationID) (*Task, error)
两个 interface 分离：计划刷新只负责远端投影；task 供应只负责本地执行实例。 进入数采任务页、手动刷新和周期任务调用前者；点击准备和完成录制后的自动衔接调用后者。

建议 HTTP interface

  • POST /api/v1/operator/plans/refresh：刷新并返回认证数采员在当前设备上的计划。
  • POST /api/v1/dc-plans/:id/tasks/next：创建或复用下一条 pending task。
  • 现有 task config / Recorder RPC contract 保持不变。
07

事务与错误处理

场景处理对执行任务的影响
Hilbert 查询或分页失败不提交计划变化，返回本地投影和 stale 状态。无。
完整快照中计划消失事务内将计划标记 inactive。停止供应下一条；ready 及以后不变。
target_count 增加不预生成；下一次 EnsureNextTask 继续供应。无。
target_count 减少达到新目标后停止供应，并取消唯一 pending，确保 next-task interface 不再返回它。ready 及以后不变。
operator / device 变化下一条 task 使用新投影重新解析资源。当前 task 保留旧快照。
并发点击准备 / 自动准备锁定 plan，复用唯一 pending。不会重复创建。
08

实施与验收

实施顺序

  1. 计划同步改为完整快照事务，只更新 dc_plan，移除同步后的批量 task generation。
  2. 新增 operator plan refresh endpoint，页面进入和刷新按钮复用。
  3. 将现有 generation 实现收缩为 EnsureNextTask，每计划最多一条 pending。
  4. 配置页面按计划请求 next task；完成录制后复用同一 interface 自动准备。
  5. 为计划刷新失败、target 增减、计划移除、并发准备和快照不可变补测试。

验收标准

  • 同步 target_count=1000 的计划后，不创建任何 task。
  • 第一次点击准备只创建一条 pending，并成功下发为 ready。
  • 重复或并发请求 next task 不产生第二条 pending。
  • 完成录制后，未达到目标时只创建并准备下一条。
  • target 增加后继续供应；target 减少到已承诺数量时停止供应。
  • 计划 operator/device 变化不修改当前 ready/in_progress task，下一条使用新快照。
  • Hilbert 不可用时页面仍展示本地计划和上次同步时间。
  • 完整快照中计划消失后不再供应新 task，历史 task / episode 可继续查询。

DEVELOPMENT DESIGN / KEYSTONE + SYNAPSE + ORBIT

Ego Portal E2
多模态转换

把 Data Gateway 上传的原始 tar，变成可验证、可同步的 H.264 MCAP 与独立 calibration.json。

核心判断

原始 tar 只做扩展名 QA；转换结果独立质检；自动同步只发送转换后的 MCAP 与 calibration.json。

FINAL
DECISION

E2 是一条独立的 derivative pipeline：
tar → H.264 MCAP + calibration.json → 派生 QA → Hilbert 同步。

01

背景与问题

现有 Keystone 已经有 Ego Portal Stereo 的 Orbit 派生处理、自动同步、派生 QA 与 ParamFile 同步能力。Ego Portal E2 的上传方式相同地经过 Data Gateway，但原始文件不是 MCAP，而是一个 tar 包；tar 解压后包含两路独立视频、IMU CSV 与相机参数。

输入事实

capture.tar
├── Camera0/video.mp4              # HEVC / H.265
├── Camera0/camera_params.json
├── Camera1/video.mp4              # HEVC / H.265
├── Camera1/camera_params.json
└── Sensors/
    ├── accel.csv
    ├── gyro.csv
    └── imu_calibration.json        # 第一版不读取

当前样例为 1600×1200、约 30 FPS；Camera0 与 Camera1 的帧数可能不同，转换只输出前 min(left_count, right_count) 对。

不能把 E2 tar 当成普通 MCAP。原始 Episode QA 只检查 .tar 后缀；转换后的 MCAP 和 calibration.json 由独立的 E2 Manager 验证。
02

目标与非目标

本次目标

  • Data Gateway 根据服务端精确设备型号 Ego Portal E2 生成 capture.tar。
  • 新增 e2-multimodal-conversion Job 镜像及独立生命周期模块。
  • HEVC 双路流式解码并编码为逐帧 H.264 access unit。
  • 生成混合编码 MCAP：Foxglove Protobuf 视频 + ROS 2 Humble CDR IMU。
  • 生成独立 calibration.json、标准 rosbag2 YAML metadata 与 manifest。
  • 自动同步只上传转换后的 MCAP 与 calibration ParamFile。
  • Synapse 提供单 Episode 操作、下载和处理配置。

明确不做

  • 不把原始 tar 上传到 Hilbert。
  • 不读取 Sensors/imu_calibration.json 或 sensor_time_to_utc.csv。
  • 不计算、不校验、不要求原始 tar checksum。
  • 不覆盖 episodes.mcap_path；它仍指向原始 tar。
  • 不做 E2 conversion 批量处理。
  • 第一版不接入 mcap_to_mp4.py，不做前端视频预览。
  • 不新增 device_type_snapshot 数据库字段。
  • 不抽取 Stereo Split 的通用大框架。
03

方案总览

Data Gateway认证设备与任务绑定；E2 生成 capture.tar；保存 duration 与录制时间。
原始 QA进入现有 QA 队列，只运行 tar_extension。
Orbit Job解压、HEVC→H.264、写 MCAP、生成 calibration。
派生 QA校验四个输出、MCAP 可读性与 calibration JSON。
Cloud SyncParamFile 先行，随后绑定并上传 output_bag.mcap。

04

上传与原始 QA

服务端决定格式

E2 客户端继续复用 Ego Portal Stereo/Lite 的 Data Gateway 上传合同：task_id、capture_id、duration 与录制时间照常携带；客户端不需要新增 product = ego_portal_e2。服务端在创建 upload session 时，依据已认证设备与已绑定任务关联出的 robots.device_type 做精确匹配。

device_type == "Ego Portal E2"
    → .../<upload_id>/capture.tar
else
    → .../<upload_id>/capture.mcap

该 device_type 冻结在 upload session 中，创建会话和完成上传使用同一个判断。E2 不使用 camera_serial，不匹配既有 camera calibration；原始 checksum 完全忽略。

Episode 创建

Data Gateway 完成业务上传时，E2 仍创建普通 Episode，继续复用 episodes.mcap_path 保存 tar 的对象 key。sidecar_path 为空；file_size_bytes、duration_sec、recording_started_at、recording_finished_at 来自上传请求。原始 QA 初始为 pending_qa，然后进入现有 QA 队列。

tar_extension

EpisodeQAHandler 根据精确设备型号分流。E2 只读取数据库中的 episodes.mcap_path，不访问 tar 内容、不检查 Content-Type、不解压、不计算 checksum。

路径后缀结果后续
.tar / .TARtar_extension passed，Episode qa_status = approved自动同步可启动 conversion；手动 process 可用。
.mcap、.tar.gz 或无后缀tar_extension failed，Episode qa_status = failed自动和手动 conversion 均禁止。

conversion 创建后，原始 QA 的重跑规则参考既定方案：没有 derivative 或 derivative 已 failed/canceled 时允许重新执行；queued/submitting/pending/running/verifying/succeeded 时禁止重跑。失败时不提供强制启动入口。

05

Job 输入、转换与输出

Job 镜像与配置

新增独立镜像：

ghcr.io/archebase/e2-multimodal-conversion@sha256:<digest>

镜像配置像 Stereo Split 一样落数据库，初始未配置；管理员必须写入真实 immutable digest 后才能执行。配置独立于 Stereo Split：

  • image_ref
  • max_concurrent，默认 1
  • resource_limits_enabled，默认 true

固定资源默认值：requests 为 CPU 4、内存 8Gi、临时盘 20Gi；limits 为 CPU 8、内存 16Gi、临时盘 100Gi。

输入目录

Job 支持 tar 内容直接位于根目录，或存在一层顶级包装目录；拒绝更深或不明确的结构。转换实现内部检查：

Camera0/video.mp4
Camera0/camera_params.json
Camera1/video.mp4
Camera1/camera_params.json
Sensors/accel.csv
Sensors/gyro.csv

这些是 Job 输入合同，不是原始 Episode QA 合同。tar 解压必须拒绝绝对路径、路径穿越、符号链接逃逸、硬链接逃逸、设备文件、FIFO/socket；普通文件总声明大小上限 60GiB，单文件上限 50GiB，member 数量上限 10,000。

视频管线

参考 Stereo Split 的 H.264 管线，但 E2 独立实现，不依赖 Stereo Split 文件或镜像。两路 HEVC 同时流式解码和编码，不把全量帧放进内存：

Camera0 HEVC ─┐
              ├─ ffmpeg decode → libx264 encode → H.264 Annex-B access units
Camera1 HEVC ─┘
  • 保持输入方向、分辨率，不裁剪、不旋转、不缩放、不交换左右。
  • 从两路输入推导共同 nominal FPS；当前样例约 30 FPS，不无条件硬编码。
  • 编码固定使用 libx264、medium、high、yuv420p、B-frame 0、GOP 30、AUD 与 repeat headers；目标码率 12M、maxrate 12M、bufsize 24M。
  • 每条视频消息对应一个视频帧的 H.264 access unit。
  • 左右帧数取最小值，较长一路尾部丢弃并写入统计。

MCAP 合同

TopicSchema / encodingframe_id / 内容
/camera/left/image/h264foxglove.CompressedVideo / protobufcamera_left_optical；format 固定为 h264。
/camera/right/image/h264foxglove.CompressedVideo / protobufcamera_right_optical；format 固定为 h264。
/imu/datasensor_msgs/msg/Imu / ROS 2 Humble CDRimu；accel 与 gyro 精确时间交集。

视频 PTS 的 time base 为微秒时乘 1000 写入 MCAP 纳秒时间；IMU CSV 的 ts_ns 直接使用。protobuf timestamp、MCAP log_time 与 publish_time 保持一致。所有视频与 IMU 消息按 timestamp 稳定归并后交错写入。

输出文件

derived/episodes/<episode-id>/e2-multimodal-conversion/g<generation>-<suffix>/
├── output_bag.mcap
├── metadata.yaml
├── calibration.json
└── processing_manifest.json

四个文件共用 generation-specific prefix。metadata.yaml 必须是真正的标准 rosbag2 YAML，不复制 Stereo Split 当前“JSON 内容、yaml 文件名”的历史格式。视频 topic 使用真实 foxglove.CompressedVideo 类型；不承诺 ros2 bag play 完整支持自定义 Protobuf 视频。

07

派生 QA 与 manifest

E2 Manager 自己执行派生输出验证，不调用现有 EpisodeQAHandler。输出合同验证失败属于 processing 失败；合同验证成功后，若后续派生 QA 失败，则保持 processing succeeded、qa failed。两套状态不互相覆盖。

output_bag.mcap

  • 存在且非空
  • 首尾 MCAP magic 正确
  • MCAP reader 可以打开
  • manifest 中 size/SHA-256 与对象一致

第一版不在派生 QA 中强制检查 topic、schema、消息数量或左右帧统计。

calibration.json

  • 存在且非空
  • manifest 中 size/SHA-256 与对象一致
  • 内容可解析为 JSON object

不校验具体 calibration schema；不绑定 camera_serial、session 或 capture。

manifest v1

manifest 固定 schema_version = 1、kind = e2_multimodal_conversion，记录 ROS 2 Humble、topic、编码参数、左右配对统计与三个输出的 size/SHA-256。原始 tar 的 source.sha256 省略；原始输入只记录 URI 与 size（以及 Keystone 冻结的 ETag）。

{
  "schema_version": 1,
  "kind": "e2_multimodal_conversion",
  "output_format": "h264_ros2_mcap",
  "ros_distribution": "humble",
  "source": {"uri": "tos://.../capture.tar", "size_bytes": 123456},
  "outputs": {
    "mcap": {"name": "output_bag.mcap", "size_bytes": 1, "sha256": "..."},
    "metadata": {"name": "metadata.yaml", "size_bytes": 1, "sha256": "..."},
    "calibration": {"name": "calibration.json", "size_bytes": 1, "sha256": "..."}
  },
  "stats": {"left_video_frames": 0, "right_video_frames": 0, "imu_messages": 0},
  "started_at": "...",
  "finished_at": "..."
}
08

自动同步与 ParamFile

自动编排

参考 Stereo Split，autosync.Manager 每轮最多推进一项工作：

  1. auto sync 开启且 E2 原始 QA approved、没有 E2 derivative：调用 e2conversion.Start()。
  2. conversion 成功且 derivative QA approved：enqueue 普通 Episode sync。
  3. 自动同步关闭：不自动创建 conversion，也不自动 enqueue sync；管理员仍可手动完成整个流程。
  4. 自动同步重新开启：补处理已有 auto_sync_requested = true 且已成功、未同步的 E2 derivative。

无论 conversion 是自动创建还是管理员手动创建，只要同步时自动同步开启且条件满足，就可以自动同步；自动同步关闭不取消已经创建的 conversion。

同步 source snapshot

扩展现有 source 类型白名单，增加 e2_multimodal_conversion。从 derivative 读取：

SourceType                 = e2_multimodal_conversion
Backend                    = tos
ObjectKey                  = .../output_bag.mcap
SizeBytes / SHA256         = MCAP 输出元数据
DerivativeID / Generation  = 当前 derivative 身份
CalibrationObjectKey       = .../calibration.json
CalibrationSizeBytes       = calibration 输出大小
CalibrationSHA256          = calibration 输出 SHA-256

复用现有字段 calibration_result_uri、calibration_result_etag、calibration_result_size_bytes、calibration_result_sha256 保存 E2 calibration 输出；URI 使用完整 tos://bucket/object。

严格同步顺序

1. 注册/恢复 Hilbert ParamFile（WorkspaceID + calibration SHA-256 + size）
2. 上传 calibration.json
3. FinishParamFileUpload
4. 注册 Hilbert RawData，并绑定 ParamFileMotionStoreID
5. 上传 output_bag.mcap
6. FinishRawDataUpload

E2 calibration 任一步失败，整个同步失败，MCAP 不单独上传。重试复用同一 sync log 和已保存的 ParamFileMotionStoreID；ParamFile 已 READY 时直接继续 MCAP。E2 手动同步不要求 auto_sync_requested。

Hilbert 的 bagName 继续使用稳定的 <episode-public-id>.mcap。录制时间优先使用 Data Gateway 携带的 recording start/end；若两者都缺失，沿用现有 created_at + duration 的 fallback。E2 Job 不解析设备单调时间到 UTC。

Server 生命周期

Server 在 Orbit URL 可用时创建独立 E2 Manager，注入 Orbit client 与 TOS object reader，接入 autosync.Manager；启动和停止独立的 reconciler 与 verification workers。Orbit URL 未配置或 E2 image_ref 未配置时，自动流程等待，手动接口返回明确 unavailable/configuration 错误。

来源与锁定

  • E2 conversion 只能接受 ingestion_channel = data_gateway 与 storage_backend = keystone_tos。
  • E2 只能同步 e2_multimodal_conversion，永远不能 fallback 到 original tar。
  • 同步 claim 仍由现有 Episode 行锁与 source snapshot 机制保证。
  • 原始 tar 与所有成功/失败 generation 默认保留；失败 generation 的四个输出未来必须成组清理。

权衡、风险与缓解

取舍 / 风险决定缓解
复用 mcap_path 保存 tar，字段名不准确第一版小改动复用E2 专属模块按 original tar 解释；禁止普通 original sync。
两套 Manager 存在生命周期代码重复独立实现，不先抽通用框架参考 Stereo Split；只共享稳定的低层约定，未来有第二个真实适配器再抽象。
底层 mcap.Writer 与 rosbag2 metadata 兼容混合 Protobuf + CDR；生成真正 YAMLmanifest 与 MCAP 独立验证；兼容目标是 MCAP/Foxglove，不承诺 ros2 bag play。
HEVC 双路转码 CPU/临时盘压力独立资源与并发，固定 4/8 CPU、8/16Gi、20/100Gi流式管线、tar 解压上限、提交前容量预检、独立 max_concurrent。
原始 tar 没有 checksum不要求、不计算、不校验提交前冻结 URI、ETag、size；最终 MCAP/calibration 强制 SHA-256。
calibration 缺失导致半成品同步calibration 失败阻止整个同步ParamFile 先行、复用 sync log 与 ParamFile ID。
原始 QA 过弱只按约定检查 .tar 后缀conversion Job 对目录、输出文件和 MCAP 可读性做第二层验证。
device_type 实时变化影响历史 Episode第一版沿用实时关联，不新增 snapshot 字段服务端精确匹配；同时要求 .tar、provenance 与 QA 门禁。
12

实施与验证

  1. Job：从本地转换脚本提炼 E2 converter；实现安全解压、双路 HEVC→H.264、MCAP writer、calibration 与 manifest。
  2. Job 测试：使用小型合成 HEVC fixture 覆盖根目录/一层包装目录、帧数不一致、H.264 message、IMU 交错、输出校验和失败路径。
  3. Data Gateway：将已绑定精确 device_type 冻结到 upload session；E2 生成 capture.tar；其他设备行为不变。
  4. 原始 QA：增加 tar_extension 分支及重跑门禁；测试大写后缀和非 tar 后缀。
  5. e2conversion Manager：参考 Stereo Split 接入 Start/Get/Retry/Cancel/Logs/QA、Orbit reconcile、验证 worker 与 server lifecycle。
  6. 自动同步：增加 E2 的 capture、Start、approved derivative sync 分支；确保不进入 original fallback。
  7. Sync Worker：增加 E2 source snapshot、ParamFile 直接读取 derivative 输出、calibration 失败阻断逻辑与 source claim。
  8. API/前端：增加 E2 Data Ops API、presign、EpisodeDetail 面板和 SystemSettings 配置区。
  9. 真实验收：使用 ~/Downloads/E2 打包为 tar 做发布前端到端验证；不把完整样例提交到仓库。

验收清单

  • E2 Data Gateway session 生成 capture.tar，Stereo/Lite 仍生成 capture.mcap。
  • E2 只进入 tar_extension QA；非 tar 无法启动 conversion。
  • 成功 Job 生成 H.264 MCAP、真正 YAML metadata、calibration.json、manifest。
  • MCAP 包含 E2 专用 topic；每个视频消息是一帧 H.264 access unit。
  • 左右视频按 min 帧数输出，消息与 IMU 按时间交错。
  • 原始 tar 不需要 checksum；MCAP 和 calibration checksum 必须有效。
  • 普通 sync 对已通过的 E2 自动选择 e2 derivative；未完成时绝不上传 tar。
  • ParamFile 未 READY 时 MCAP 不上传；失败重试复用 ParamFile。
  • 自动同步关闭时手动 process/sync 可用；开启时手动 process 成功后可自动补同步。
  • 原始 tar、成功/失败 generation 均不被本功能自动删除。
回滚原则：镜像配置可恢复到空或上一 digest；已创建的 E2 derivative 停止自动推进但不删除原始 tar；source claim 与已完成同步记录不可回滚覆盖。

本功能不一次性合并。每个 PR 保持一个可验证的变化面，先建立 Job 合同，再接入上传、QA、生命周期、同步和前端。每个阶段完成测试后独立 commit。

PR 0：设计文档

只提交当前 HTML 文档，不修改业务代码。

docs(keystone): add Ego Portal E2 conversion design

PR 1：独立 E2 conversion Job

新增 keystone/jobs/e2-multimodal-conversion/，实现安全解压、双路 HEVC 流式转 H.264、混合编码 MCAP、calibration.json、真正的 rosbag2 YAML metadata 与 manifest。Job 独立实现 Foxglove descriptor，不依赖 Stereo Split。

使用小型合成 HEVC fixture 做 CI 测试；使用 ~/Downloads/E2 打包后的真实样例做本地发布前验收，不提交完整样例。

feat(e2-conversion): add E2 tar to H264 MCAP job

PR 2：Data Gateway 的 capture.tar

服务端依据已绑定任务的精确 robots.device_type，将 Ego Portal E2 的对象名生成 为 capture.tar，并将 device type 冻结到 upload session；Stereo/Lite 继续生成 capture.mcap。

feat(dgwcompat): store Ego Portal E2 uploads as tar

PR 3：原始 tar_extension QA

E2 进入现有 QA 队列，但只执行大小写不敏感的 tar 后缀检查。非 tar 不能启动 conversion；原始 QA 与派生 QA 状态保持独立。

feat(qa): add Ego Portal E2 tar extension check

PR 4：数据库配置与领域值

新增 v2/000021_e2_multimodal_conversion migration，创建独立 image config 表并扩展 cloud source 白名单。复用 episode_derivatives 现有 calibration_result_* 字段，不新增 calibration 字段。

feat(db): add E2 conversion processing configuration

PR 5：e2conversion.Manager

新增独立的 E2 conversion 模块，参考 Stereo Split 实现 Start/Get/Retry/Cancel/Logs/RetryQA、Orbit reconciler、输出验证、派生 QA 和 Server 生命周期；第一版不做批量 conversion。

feat(e2-conversion): add durable Orbit processing lifecycle

PR 6A：自动同步编排

扩展 autosync.Manager：原始 QA 通过后自动启动 E2 conversion；处理成功且派生 QA 通过后自动进入普通 Episode sync；关闭自动同步不取消已启动 Job，重新开启后补同步既有合格结果。

feat(autosync): orchestrate Ego Portal E2 conversion

PR 6B：Sync Worker 与 ParamFile

增加 E2 source snapshot 和 source resolver。普通同步、批量同步和自动同步对已通过的 E2 统一选择 e2_multimodal_conversion，永远不上传原始 tar。ParamFile 必须先完成，失败时阻止 MCAP 上传，并复用 sync log 与 ParamFile ID 重试。

feat(sync): upload Ego Portal E2 conversion outputs

PR 7：后端 Data Ops API

新增 E2 的查询、process、retry、cancel、logs、retry QA、presign 接口，以及独立 image/concurrency/resource 配置接口。不新增 E2 专用 sync API，普通 Episode sync 由后端自动选择来源。

feat(api): expose Ego Portal E2 conversion operations

PR 8：Synapse 单 Episode UI

在 EpisodeDetail 增加 E2 面板，在 SystemSettings 增加 E2 配置区。提供手动处理、日志、成功产物下载和同步按钮；失败/取消产物不提供正式下载；不做批量 E2 conversion 和视频预览。

feat(synapse): add Ego Portal E2 conversion controls

阶段验收原则

  • PR 1 合并后，Job 可以脱离 Keystone 独立将 E2 tar 转为 H.264 MCAP 与 calibration.json。
  • PR 2–3 合并后，E2 上传对象为 capture.tar，且只有 tar_extension 通过才可继续。
  • PR 4–5 合并后，管理员可以通过后端生命周期接口创建并监控 E2 Orbit Job。
  • PR 6A–6B 合并后，自动和手动同步都只能发送转换产物，且 calibration 失败会阻止 MCAP。
  • PR 7–8 合并后，管理员可通过 API 和 Synapse 完成单 Episode 的处理、验证、下载和同步。

后端每个 PR 至少执行 gofmt、相关 Go package tests 与必要的全量测试；Job 执行对应 unittest/container smoke；Synapse 执行 npm run build。

最终落点：让格式差异停在转换模块

Data Gateway 负责正确保存输入，Episode QA 负责确认它是 tar，E2 Manager 负责把 tar 变成稳定的 H.264 MCAP，Sync Worker 负责把已经验证的两个输出完整送入 Hilbert。每个 seam 都保持明确，失败不会把原始 tar 误当成 MCAP。
